    - **SIMD** **S**ingle **I**nstruction(하나의 명령으로) **M**ultiple **D**ata(여러개의 데이터를 얻어내는 방식)
        - Core 가 처리해야 될 작업을 쓰레드 Thread 시 → 100개의 Core에 각각 하나씩 할당하는 SIMD 방법이 있음
    - 하지만 천개 Core 환경에서 백만개 Thread가 있을경우?
        - **SIMT** Single Instruction Multiple Threading 쓰레드 중심의 처리 방식.
        - 쓰레드를 묶고(예 1000개씩), Core도 묶어서(100개씩) 각각 배치(할당)하여 분배가 좀 더 쉬워짐
        - 이 경우 1000개 쓰레드를 100개 코어에서 처리해야되므로, 다시 쓰레드를 100개씩 10개로 묶어주면 10개의 그룹이 생성되는데, 이를 **warp** 라고 합니다.
        - 하나의 warp 안에는 100개의 쓰레드가 있기 때문에, 하나의 쓰레드가 각각 하나의 코어에 할당되어 연산 수행 할 수 있습니다.
    - RTX3090 GPU 는 1만개 넘는 코어가 들어가 있음.
        - 코어는 128개씩 그룹으로 묶여 있습니다. 128개 쓰레드가 들어있는 워프들이 코어그룹안에서 연산됨.
        - 워프에서 작업 중 지연 시간(메모리) 발생 시, 바로 다음 워프를 수행함으로써 계속해서 연산이 이루어지게 됨.

    - **Attention Head 12개** : 각 Transformer Block에는 Attention Head가 12개 있습니다.
        - 주변 단어로 맥락을 살피는 방법이 필요 → Self-Attention 으로 이루어진 Layer 를 통과하는 것 ⇒ 맥락 정보 주입!
        - 입력한 문장(토큰)이 Q 쿼리로도 쓰이고, K 키로도 쓰임, 즉 쿼리 키 같은 정보를 사용 ⇒ Self-Attention
        
        !mermaid-diagram (2).png.png)
        
        !https://poloclub.github.io/transformer-explainer/
        
        https://poloclub.github.io/transformer-explainer/
        
        - 전체 임베딩 차원은 768이고 Head는 12개이므로: 768 ÷ 12 = 64
        - Head 하나는 64차원을 담당합니다: 12개 Head × 64차원 = 768차원
        - Head들은 **같은 문장을 서로 다른 Weight로 분석**합니다.
        - 개념적으로는 다음처럼 이해할 수 있습니다.
            
            ```markdown
            Head 1: 가까운 단어 관계
            Head 2: 주어와 동사 관계
            Head 3: 대명사가 가리키는 대상
            Head 4: 문장 위치 관계
            ```
            
        - 실제 Head의 역할은 이렇게 정확하게 한 가지로 나뉘지는 않습니다.

        - `"오늘"`을 처리할 때는 오른쪽의 `"학교에 갔다"`를 보면 안 됩니다.
            - 나는 오늘      → 볼 수 있음

        !스크린샷 2026-07-31 오후 8.31.16.png
        
        - **scaled logit** = logit **÷ temperature**
            - Temperature는 토큰 확률의 차이를 조절합니다.
            
            ```
            **Temperature < 1**
            → 높은 점수와 낮은 점수 차이가 더 커짐
            **→ 더 확실하고 보수적인 선택**
            ```
            
        - **Top-k 필터링** : 모든 토큰 중 점수가 높은 상위 10개만 남김
            - Top-10 밖에 있는 토큰은 큰 음수 적용 → Softmax 결과 0% 됨
        - **Top-p**는 **누적 확률이 p 이상이 될 때까지** 확률이 높은 후보부터 남기는 방식입니다.
            - 다른 이름으로 **Nucleus Sampling**이라고 합니다.
            - 예를 들어: Top-p = 0.8 이면 확률이 높은 순서대로 더합니다.
            
            ```markdown
            **좋다: 35%                 → 누적 35%
            춥다: 25%                 → 누적 60%
            덥다: 15%                 → 누적 75%
            맑다: 10%                 → 누적 85%**
            이상하다: 5%               → 누적 90% : 제거
            자동차: 3%                → 누적 93% : 제거
            ...
            ```
            
            - `맑다`까지 포함했을 때 누적 확률이 80%를 넘었습니다. 따라서 후보는 다음 4개입니다. 나머지는 제거됩니다.

        !스크린샷 2026-07-31 오후 8.47.45.png
        
        - 목적은 모델이 특정 뉴런이나 특정 연결에만 너무 의존하지 않도록 만드는 것입니다.
        - 쉽게 말하면 시험공부할 때 한 문제 유형만 외우지 못하게, 일부 힌트를 가리고도 풀게 만드는 훈련입니다.
        - 왜 일부 값을 끌까?
            - Dropout이 없다면 모델이 특정 연결에 지나치게 의존할 수 있습니다.
            - 예를 들어 모델이 항상 한 특징만 보고 정답을 맞히려고 할 수 있습니다. `이 특징 하나만 있으면 무조건 정답`
        - 그러면 학습 데이터에서는 잘 맞지만, 새로운 데이터에서는 틀릴 수 있습니다.
        - 이를 **과적합(Overfitting)**이라고 합니다.
        - Dropout을 사용하면 특정 연결이 언제든 꺼질 수 있으므로 모델은 여러 특징을 함께 사용하려고 합니다.
            - `특징 A가 꺼져도 특징 B와 C를 이용해 판단`
        - 그래서 새로운 데이터에도 더 잘 대응하도록 돕습니다.

        ```markdown
        # 파라미터(Parameter)는  > 가중치를 포함한 학습 가능한 숫자 전체
        Parameter 
        ├── Weight
        ├── Bias 
        ├── Embedding 값
        └── LayerNorm의 scale, bias
        ```
        
    - (참고) PyTorch 모델의 `model.parameters()`에는 **학습 가능**한 **파라미터**
        
        ```markdown
        for name, parameter in model.named_parameters():
            print(name, parameter.shape)
            
        # 출력 확인
        token_embedding.weight
        attention.query.weight
        attention.key.weight
        attention.value.weight
        attention.output.weight
        ffn.linear1.weight
        ffn.linear1.bias
        ffn.linear2.weight
        ffn.linear2.bias
        layer_norm.weight
        layer_norm.bias
        ```
        
    - **그래디언트**(Gradient) : **기울기**
        - 그래디언트는 현재 파라미터를 **어느 방향으로 얼마나 바꾸면 오차가 줄어드는지** 알려주는 값입니다
        - 그래디언트는 모델의 지식을 직접 저장하는 값이 아니라, 지식을 저장하는 파라미터를 고치기 위한 **임시 안내값**입니다.
        - 예를 들어 현재 가중치가 다음과 같다고 하겠습니다.
            
            ```markdown
            현재 Weight = 0.50
            Gradient    = 0.20
            학습률       = 0.10
            ```
            
        - 가중치는 보통 다음 방식으로 수정됩니다.
            
            ```markdown
            새 Weight
            = 현재 Weight - 학습률 × Gradient
            ```
            
        - 계산하면:
            
            ```markdown
            새 Weight
            = 0.50 - 0.10×0.20
            = 0.48
            ```
            
        - 그래디언트가 양수였기 때문에 가중치를 줄이는 쪽으로 이동한 것입니다.
        - 반대로 그래디언트가 음수라면:
            
            ```markdown
            현재 Weight = 0.50
            Gradient    = -0.20
            학습률       = 0.10
            
            새 Weight
            = 0.50 - 0.10×(-0.20)
            = 0.52
            ```
            
        - 가중치가 커집니다.

    - **가중치 공개 모델:** 모델 파일을 내려받아 내 서버나 PC에서 직접 실행할 수 있음
        - **가중치를 공개했다고 해서 반드시 완전한 오픈소스인 것은 아닙니다.** 사용 허가 범위는 라이선스를 별도로 확인해야 합니다.
        - 모델 구조가 **두뇌의 설계도**라면, 가중치는 학습을 통해 채워진 **실제 지식과 판단 기준**에 가깝습니다.
            - 모델 구조만 있음 → 빈 두뇌에 가까움
            - 모델 구조 + **학습된 가중치** → 실제로 문장을 생성할 수 있는 모델
        - 가중치를 공개한다는 것은 학습이 끝난 모델의 숫자 파일을 사용자가 받을 수 있도록 제공한다는 뜻입니다.
            - 일반적으로 다음과 같은 파일로 배포됩니다.
                
                ```bash
                model.safetensors
                pytorch_model.bin
                *.gguf
                여러 개로 분할된 weight 파일
                ```
                
            - 사용자는 이를 다운로드해서 자신의 장비에서 실행할 수 있습니다.
    - **가중치 비공개 모델:** 일반적으로 모델 자체는 다운로드할 수 없고, 제공 회사의 API나 서비스로 사용함
        - 가중치를 비공개한다는 것은 학습된 모델 파일을 사용자에게 전달하지 않는다는 뜻입니다.

- **dtype="float16"** 비유로 설명
    - 모델의 모든 **가중치(weight)와 계산 결과는 결국 숫자**입니다. **dtype은 그 숫자 하나하나를 적을 때 사용하는 메모지의 크기**라고 생각하면 됩니다.
        - float32 = 큰 메모지 (A4 용지) → 소수점 자리까지 아주 정밀하게, 아주 크거나 아주 작은 숫자도 넉넉하게 적을 수 있음
        - float16 = 작은 메모지 (포스트잇 반쪽) → 절반의 공간이라 대충 자릿수만 적을 수 있고, 너무 크거나 너무 작은 숫자는 아예 못 적음
    - 숫자 하나를 적는 종이가 작아지니까 창고(메모리)에 훨씬 적은 공간을 차지하고 택배 상자(GPU 메모리 대역폭)로 나를 때도 절반 무게라 더 빨리 옮길 수 있습니다. ⇒ 이게 float16을 쓰는 핵심 이유 : **정밀도를 조금 희생하고 속도와 메모리를 얻는 것**입니다.
    - 부동소수점 숫자는 부호 + 지수(range) + 가수(precision)로 구성됩니다.
        
        ```python
        ┌──────────┬───────────────┬──────┬────────────┬──────────────┬───────────────────────┬────────────┐
        │  dtype   │    **총 비트**      │ 부호  │ 지수(범위)   │ 가수(정밀도)    │     표현 가능 범위       │  유효숫자     │
        ├──────────┼───────────────┼──────┼────────────┼──────────────┼───────────────────────┼────────────┤
        │ **float32**  │ **32bit** (4byte) │ 1    │ 8bit       │ 23bit        │ ±10⁻³⁸ ~ ±10³⁸        │ 약 7자리     │
        ├──────────┼───────────────┼──────┼────────────┼──────────────┼───────────────────────┼────────────┤
        │ **float16**  │ **16bit** (2byte) │ 1    │ 5bit       │ 10bit        │ ±6×10⁻⁵ ~ 65504       │ 약 3~4자리   │
        ├──────────┼───────────────┼──────┼────────────┼──────────────┼───────────────────────┼────────────┤
        │ **bfloat16** │ **16bit** (2byte) │ 1    │ 8bit       │ 7bit         │ float32와 동일한 범위    │ 약 2~3자리   │
        └──────────┴───────────────┴──────┴────────────┴──────────────┴───────────────────────┴────────────┘
        ```
        
        - float32는 "종이가 커서 자릿수(가수)도 많이 적고, 0의 개수(지수)도 많이 적을 수 있음"
        - float16은 "종이가 작아서 둘 다 줄여야 함 → 큰 숫자(65504 초과)는 아예 못 적고(overflow → inf), 아주 작은 숫자는 반올림돼서 0이 되어버림(underflow)"
        - bfloat16은 "가수 자리는 더 줄이지만 지수 자리는 float32만큼 유지" → 큰/작은 숫자 표현 범위는 그대로 두고 세밀함만 포기한 절충안 (그래서 학습 시 오버플로우에 더 안전해서 많이 씀)
        
    - LLM 서빙에서 왜 중요한가
        1. **모델 크기 절반**: 70B 파라미터 모델을 float32로 올리면 약 280GB, float16이면 약 140GB → GPU에 올라가느냐 마느냐가 갈릴 수 있음
        2. **KV 캐시도 절반**: decode 단계는 메모리 대역폭이 병목(memory-bound)인데, float16을 쓰면 캐시에서 읽어오는 데이터양이 절반이 되어 decode 속도가 실질적으로 빨라짐
        3. **GPU 텐서 코어 가속**: NVIDIA GPU는 fp16 연산에 특화된 하드웨어(Tensor Core)가 있어서 float32보다 훨씬 빠르게 행렬곱을 처리
        
    - **트레이드오프 (단점)** : 포스트잇에 억지로 자세한 숫자를 적으려다 뭉개지듯, float16도 문제가 생길 수 있습니다:
        - 값이 65504를 넘으면 **inf로 튐 (overflow)**
        - 아주 작은 gradient 값이 0으로 반올림됨 (underflow): 특히 학습(training) 시 문제가 됨 → 그래서 학습에는 bfloat16이나 mixed precision을 더 선호
        - **추론(inference) 시에는 이미 학습된 가중치를 그대로 쓰는** 거라 **오버플로우 위험이 상대적으로 적어서 float16을 무난하게 사용**
    
- **dtype 변환 vs 양자화(Quantization)** 비유로 설명 : "메모지 줄이기" vs "완전히 다른 기록 시스템으로 바꾸기”
    - **dtype 변환**(float32 → float16/bfloat16)
        - **같은 방식(**부호+지수+가수로 이루어진 부동소수점)으로 적되, **종이만 더 작은 걸 쓰는 것**. 숫자를 적는 "문법"은 그대로고, 자릿수만 줄어듦.
    - **양자화(Quantization**, 예: int8, int4)
        - 아예 **다른 기록 시스템**으로 갈아타는 것. 마치 사진을 그림물감 몇 가지 색깔(팔레트)로만 다시 칠하는 "페인트 바이 넘버(paint-by-numbers)"처럼, 원래 **연속적인 실수값**을 **정해진 개수의 정수 칸(bucket)에 억지로 끼워 맞추는** 방식입니다.
        - 예를 들어 int8 양자화는 원래 값을 -128~127 사이의 정수 256개 중 하나로 반올림해서 저장하고, 원래 값으로 되돌릴 때는 실제값 ≈ (정수값 - zero_point) × scale 이라는 환산표(scale/zero-point)를 따로 들고 다녀야 합니다. 즉, "숫자 자체"가 아니라 "팔레트에서 몇 번 색인지"만 저장하는 셈이죠.
    - 비교
        
        ```python
        ┌─────────────┬───────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
        │             │            dtype 변환 (fp32→fp16/bf16)             │                  양자화 (fp→int8/int4)                  │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 표현 방식     │ 여전히 부동소수점 (연속적)                               │ 정수 + scale/zero-point (이산적, 팔레트 방식)           │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 압축률        │ 2배 (32bit→16bit)                                  │ 4배(int8), 8배(int4) 이상                               │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 정밀도 손실    │ 상대적으로 적음, 구조적으로 안정                          │ 더 큼, calibration 안 하면 성능 급락 가능               │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 추가 작업     │ 거의 없음 (그냥 .half() 캐스팅)                        │ calibration/보정 데이터셋, 또는 QAT(양자화 인식 학습) 필요   │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 대표 기법     │ 그냥 dtype 캐스팅                                    │ GPTQ, AWQ, bitsandbytes(NF4), SmoothQuant, GGUF         │
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 하드웨어 지원  │ GPU Tensor Core가 fp16/bf16 연산 네이티브 지원         │ int8/int4 연산 지원 GPU 필요, 혹은 연산 전 "복원(dequant)" 커널 필요│
        ├─────────────┼───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
        │ 주 용도     │ 학습(bf16 mixed precision)과 추론 둘 다 기본값으로 흔히 사용 │ 주로 추론 전용, 거대 모델을 저사양 GPU/엣지에 올릴 때              │
        └─────────────┴───────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
        ```
        
    - **LLM 서빙 관점에서 실전 차이**
        - float16: 70B 모델 280GB → 140GB. GPU 여러 장(A100 등)에는 여전히 필요.
        - int8 양자화: 140GB → 70GB. 소비자용 GPU 한두 장으로도 시도 가능해짐.
        - int4 양자화: 70GB → 35GB. 노트북/엣지 디바이스에서도 거대 모델 구동 가능.
        - 다만 int4까지 가면 "팔레트 색깔 수"가 너무 적어져서(16개 수준) **모델 성능(정확도)이 눈에 띄게 떨어질** 수 있어, **GPTQ·AWQ 같은 똑똑한 팔레트 선택 알고리즘**(어떤 가중치가 더 중요한지 분석해서 오차를 최소화)이 **필요**합니다.
        
    - **정리**
        - dtype 변환은 "같은 언어로 더 작게 쓰기" : 손실이 적고 거의 공짜로 적용 가능
        - 양자화는 "아예 다른 압축 언어로 번역하기" : 압축률은 훨씬 높지만, 번역이 서툴면(calibration 부실) 의미(정확도)가 크게 왜곡될 위험이 있음
        - 실무에서는 흔히 "우선 float16/bfloat16으로 절반 줄이고, ⇒ 그래도 메모리가 부족하면 양자화(int8/int4)를 추가로 적용"하는 단계적 접근을 씁니다.
