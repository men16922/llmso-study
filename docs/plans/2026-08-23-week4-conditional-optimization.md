## 글의 축 — 교재가 스스로 밝혀 놓았다

`study/Ch7.md:12`의 첫 질문이 그대로 축이다:

> *"compute-bound vs memory-bound" 축이 이 장 전체를 관통하는 단일 기준이라는 걸 어떻게 설명할 수 있는가?*

추측 디코딩은 memory-bound·저배치에서만 이득이고, PD 분리는 prefill(compute-bound)과 decode(memory-bound)의 간섭을 없애려는 것이고, MoE의 희소성도 배치 크기가 이 경계를 어디로 미느냐의 문제다. **CH7의 네 기법이 전부 "조건부로만 이득"이고 조건이 하나의 축이다.**

그리고 그 조건이 코드 어디에 있는지는 CH8이 답한다. `study/Ch8.md:9`:

> *num_computed_tokens와 num_tokens_with_spec의 차이를 좁히는 것이 왜 청크드 프리필·프리픽스 캐싱 같은 모든 최적화의 공통 메커니즘이 되는가?*

**chunked prefill · prefix caching · 추측 디코딩은 vLLM 스케줄러에서 같은 한 가지를 바꾼다** — 한 스텝에 토큰 예산을 어디에 쓰느냐. 그래서 CH7(측정)과 CH8(설명)이 한 글에 들어간다.

### 3주차와의 연결

3주차 결론은 *"구조가 설정의 상한을 정한다"* 였다. 4주차는 그 다음 칸이다 — **상한 안에서 설정을 조일 때, 어떤 노브는 조건부로만 이득이고 그 조건은 읽을 수 있다.**

**PD 분리의 대역으로 chunked prefill을 쓴다.** "prefill이 decode를 밀어낸다"는 같은 문제를 GPU 1장에서 다루는 방식이고, 그래서 PD 분리의 동기를 실측으로 설명할 수 있다.

## ★ 통제 변수 — 3주차에 데인 자리

3주차의 가장 큰 함정이 **이미지마다 품은 vLLM 버전이 달라 계층 비용에 엔진 버전 차이가 섞인 것**이었다. 같은 실수를 반복하지 않기 위한 이번 주 원칙:

**실험 A·B·C를 전부 `vllm/vllm-openai:v0.23.0` 하나 위에서 돈다.** 이미 로컬에 있고(2주차 B1 기준선), 추가 다운로드 0이며, V1 엔진이라 세 기능이 모두 살아 있다.

⚠️ **A를 ray-llm(vLLM 0.7.2, V0)에서 돌리고 싶은 유혹을 참을 것.** 3주차 메모에 *"0.7.2는 V0라 `chunked_prefill_enabled=False`가 기본이라 ON/OFF 비교가 가능하다"* 고 적혀 있지만, 그렇게 하면 **A만 다른 엔진에서 나온 숫자**가 되어 B·C와 같은 표에 못 넣는다. V1에서는 축을 `--max-num-batched-tokens` 크기로 바꾸면 같은 질문을 같은 엔진에서 잴 수 있다(작게 = 프리필이 잘게 쪼개져 디코드와 섞임, `max_model_len` 이상 = 사실상 통짜 프리필).

## 먼저 확인할 것 (측정 전, GPU 없이 가능)

플래그 이름과 메트릭 이름을 **추측하지 말고 0.23.0에서 직접 확인한다.** `docker run --rm vllm/vllm-openai:v0.23.0 --help` 한 번이면 된다.

- [ ] `--speculative-config`의 실제 스키마 — ngram / draft model 각각의 키
- [ ] draft model 방식이 V1에서 지원되는가 (ngram·EAGLE만 되는 버전대가 있었다)
- [ ] prefix caching을 끄는 플래그 (`--no-enable-prefix-caching` 형태로 추정)
- [ ] `--max-num-batched-tokens` 하한 (엔진이 거부하는 값이 있다)
- [ ] 메트릭 이름 — `vllm:spec_decode_*`(수용률), `vllm:prefix_cache_{queries,hits}_total`

이걸 안 하면 3주차의 `accelerator_type: null` 같은 **조용한 실패**를 다시 겪는다. 파드는 정상인데 기능만 안 켜져 있고 로그에도 안 남는 종류다.

## 실험 설계

### A — chunked prefill: 프리필이 디코드를 밀어내는 값

**축**: `--max-num-batched-tokens` (예: 512 / 2048 / 8192)
**부하**: 긴 프롬프트 + 짧은 출력(프리필 지배) 요청과 짧은 프롬프트 + 긴 출력(디코드 지배) 요청을 **섞어서** 동시에 넣는다. 섞지 않으면 간섭이 안 보인다.
⚠️ `benchmark.py`는 시나리오를 **순차로** 돈다(`run_scenario`가 시나리오마다 별도 executor). `--scenarios prefill,decode`로는 안 섞인다 — **두 프로세스를 동시에 띄우는 것**이 코드 수정 없는 유일한 방법이다.
**보는 것**: 디코드 요청의 **ITL**이 프리필 요청 때문에 얼마나 튀는가. 청크를 작게 하면 ITL 지터가 줄고 프리필 TTFT는 늘어야 한다 — 그 교환비가 결과.
**왜 이게 PD 분리 이야기인가**: 같은 GPU에 둘이 있으면 반드시 서로를 민다. 청크는 그 간섭을 잘게 나눠 완화할 뿐 없애지 못한다. 없애려면 물리적으로 분리해야 한다 = PD 분리.
**다운로드**: 0GB · **3주차 이월분 ③-b 해소**

### B — 추측 디코딩: 이득이 뒤집히는 지점 ★ 주인공

**팔**: vanilla / ngram / draft-model(`Qwen/Qwen2.5-0.5B-Instruct`)
**축**: 동시성 1 · 4 · 16 · 64
**보는 것**: ITL·TPOT(이득이 나타나는 자리)와 처리량(손해가 나타나는 자리). 그리고 **수용률** — 이득을 가르는 진짜 변수.
**가설**: 저동시성에서는 ITL이 개선되고, 고동시성에서는 처리량이 **떨어진다**. 배치가 이미 GPU를 채우고 있으면 draft 토큰 검증은 순수한 낭비 연산이기 때문.
**출발점이 교재에 있다** — `Ch7.md:949`: *"동시성 1 환경에서 vanilla 모델에서 이미 GPU 98% 사용 → 이후 추측성 디코딩 실습 시 오히려 역효과!"* 이 관측을 재현하고 **왜 그런지를 축으로 설명**하는 게 이 실험의 목표다.
**주의**: 12GB에 target 1.5B + draft 0.5B가 같이 올라간다. `gpu_memory_utilization`을 다시 잡아야 하고, 그러면 KV 예산이 바뀌어 **vanilla 팔과 KV 예산이 달라진다**. 기동 로그의 KV 예산을 세 팔 모두 기록해 비교 가능 여부를 먼저 판정할 것. ngram 팔은 이 문제가 없다(모델 추가 없음).
**다운로드**: ngram 0GB / draft ~1GB

### C — prefix caching: 공유 프리픽스가 있을 때만

**축**: 서버 캐시 ON/OFF × 클라이언트 공유 ON/OFF = **2×2** (도구 수정 불필요)
**보는 것**: TTFT와 `vllm:prefix_cache_hits_total / queries_total`
**선행 작업 없음.** `benchmark.py`를 확인하니 필요한 게 이미 다 있다 — `prefill` 시나리오의 프롬프트가 같은 문단을 **24회 반복**한 긴 문맥이라(`benchmark.py:30`) 요청들이 통째로 공유하고, `--unique-prefix`(`benchmark.py:160`)가 UUID를 앞에 붙여 **일부러 적중을 막는다**. 서버의 캐시 ON/OFF와 곱하면 **2×2**가 그대로 나온다.
**축과의 연결**: 캐시 적중은 프리필 연산을 통째로 건너뛴다 = compute-bound 구간을 지운다. 공유가 없으면 순수 오버헤드.
**다운로드**: 0GB · **도구 수정 0**

### D — vLLM 스케줄러 해부 (설명층)

컨테이너 안의 `vllm/v1/core/sched/scheduler.py`를 직접 읽고, A·B·C가 **같은 토큰 예산 계산의 어느 항을 건드리는지**를 코드로 짚는다. GPU도 다운로드도 불필요하므로 측정을 기다리는 동안 진행한다.

이게 없으면 글이 *"재 봤더니 이렇더라"* 에서 멈추고, 있으면 *"왜 그런가"* 까지 답한다. **3주차 글과의 차별점이 여기 있다.**

## 잘라내기 순서 (분량·시간 초과 시)

1. **B의 draft 팔** — ngram만으로도 "조건부 이득"은 증명되고, KV 예산 문제도 함께 사라진다
2. **A의 중간 청크 크기** — 512/8192 양 끝만
3. **C의 캐시OFF×공유OFF 칸** — 2×2 중 오버헤드 확인용이라 없어도 결론은 선다
4. **D를 부록으로** — 본문에서 빼고 부록 A로

**B의 동시성 축은 자르지 않는다.** 이득이 뒤집히는 걸 보여주는 게 글의 핵심이라 양 끝(1과 64)이 반드시 필요하다.
