# 5주차 글의 추가 검증과 실험 우선순위

작성일: 2026-09-05

대상은 [5주차 원고](../../articles/처리량이%20올랐다면%20무엇이%20빨라진%20것인가.md)입니다. 사용자의 ‘더 임팩트 있는 포스팅에 필요한 추가 실험’ 요청을 검토한 계획이며, 아래 GPU 실험은 아직 실행하지 않았습니다.

## 1. 먼저 해결할 것은 새 실험보다 원본 집계다

09-05 초안 작성 당시 이 체크아웃에는 `results/f*`, `f-analysis.md`, `run_f*.sh`가 없었습니다. **같은 날 원격 `d37fbae`까지 동기화하면서 결과·실행 스크립트·F2 압축 트레이스 2개·`summarize_trace.py`를 확보했습니다.** 이제 아래 순서로 원본과 대조합니다. 파일 확보가 원측정 재현이나 집계 검증 완료를 뜻하지는 않습니다.

| 확인할 자료 | 검증할 내용 | 글에 반영할 결과 |
| --- | --- | --- |
| F1b 구성별 원시 JSON·기동 로그 | 반복별 성공 요청·입출력 토큰·처리량, 평균·σ 산식, 실제 KV 예산 | 3회 평균과 ±1σ 그래프 검증 |
| F2 BF16·FP8 트레이스와 집계 코드 | 프로세스·스트림·이벤트 종류, 중복 집계, 어텐션 호출 수, 분모 | 58·98스텝 및 28배 차이 해소 |
| F1c 원시 JSON | tok/s 필드가 생성·프롬프트·전체 중 무엇인지 | 워크로드 표의 지표 이름 확정 |

현재 산술상 확인되는 것은 `503.1 / 58 = 8.67ms`, `622.8 / 98 = 6.36ms`입니다. 기존 309.77·226.96µs는 다시 28로 나눈 값과 거의 같습니다. 하지만 어텐션 커널 하나가 레이어·스텝마다 한 번 호출됐는지와 역할 분류는 원본으로 확인해야 합니다. 커널 duration 합계와 실제 스텝 elapsed time도 구분합니다.

원본을 복구할 수 없으면 같은 작업량으로 F1b·F2를 다시 측정합니다. 비교마다 예열, 요청 수, 실제 입력·생성 토큰, 배치 크기, GPU 상태를 기록합니다. 프로파일러를 켠 실행의 처리량은 일반 성능 비교에서 분리합니다. 반복 수를 늘리는 것만으로 측정 조건의 차이가 해결되지는 않습니다.

## 2. 새 실험 하나를 고르면 KV 여유에 따른 2×2 비교

**질문: FP8의 이득은 KV 공간이 넉넉할 때와 부족할 때 어떻게 달라지는가?**

현재 원고는 여유 구간의 FP8 비교와 부족 구간의 BF16 실험이 따로 있습니다. 같은 워크로드에서 두 축을 교차하면 CH9의 메모리 효과와 이번 실험의 처리시간 효과를 한 그림에서 설명할 수 있습니다.

| 구성 | 양자화 | KV 예산 |
| --- | --- | --- |
| A | BF16 | 여유 |
| B | FP8 | A에 맞춘 여유 예산 |
| C | BF16 | 부족 |
| D | FP8 | C에 맞춘 부족 예산 |

모델·이미지·프롬프트·생성 길이·동시성은 모두 고정합니다. 긴 입력과 동시성 64를 후보로 삼되, 짧은 예비 측정으로 실제로 KV 압박이 생기는 지점을 찾습니다. `gpu_memory_utilization` 값이 아니라 기동 로그의 KV 토큰 용량을 맞춥니다. 캐시 재사용을 통제하고, 실제 생성 길이 차이가 있으면 그대로 기록해 해석에 반영합니다.

권장 실행은 구성별 예열 후 최소 5회입니다. A→B→C→D만 반복하지 말고 순서를 교차해 온도·클록·실행 순서의 영향을 줄입니다. 예산을 정확히 맞추지 못했다면 잔여 차이를 공개합니다. 이 실험은 운영 부하의 성능을 비교하므로 대기와 선점도 결과에 포함합니다.

**지표는 네 가지면 충분합니다.** 프롬프트 처리량, TTFT p50·p95, 선점 증가량, 대기 요청 수입니다. 생성 처리량도 저장하되 입력 처리량과 같은 축에 섞지 않습니다. 성능 원시 JSON과 함께 구성·시간·기동 로그·메트릭 구간을 보관합니다.

**예상 그림:** 가로축은 KV 여유/부족, 세로축은 같은 지표의 처리량, BF16·FP8 두 계열과 반복 오차를 표시합니다. 아래에는 TTFT와 선점을 붙입니다. 결과를 보기 전에 ‘부족 구간에서는 반드시 FP8이 더 좋다’고 결론을 정하지 않습니다. 상호작용이 있으면 KV와 커널 효과를 단순한 기여율로 더하거나 빼지 않습니다.

이 실험이 있으면 제목과 결론을 ‘FP8으로 33% 빨라졌다’에서 ‘KV 여유에 따라 달라지는 양자화의 효과’로 확장할 근거가 생깁니다. 현재 글에는 미실행 설계를 결과처럼 넣지 않았습니다.

## 3. 원인을 더 좁히려면 같은 작업량의 프로파일링

본문을 ‘KV 예산 증가만으로는 설명되지 않는다’에서 ‘어떤 커널의 무엇이 줄었다’까지 확장하려면 필요합니다.

- BF16·FP8에서 같은 실제 배치와 입력·생성 길이의 안정 구간을 캡처합니다. 동시 요청 수만 같다는 이유로 배치가 같다고 가정하지 않습니다.
- PyTorch Profiler로 연산과 커널을 연결하고, 겹친 이벤트를 중복 합산하지 않습니다. 시간 합계를 스텝 수로 나눈 값과 타임라인에서 잰 경과시간을 모두 남깁니다.
- Nsight Systems로 CPU 대기·GPU 실행·동기화를 구분합니다. 대역폭이 원인이라고 주장하려면 Nsight Compute에서 지배적인 GEMM의 실제 메모리 이동과 연산 지표를 대조합니다.
- 정확한 Nsight 메트릭 이름은 설치 버전과 GPU에서 조회해 정합니다. 프로파일러 설치·권한 변경은 측정 환경 확인 후 별도 작업으로 진행합니다.

이 검증 전에는 ‘가중치 읽기 대역폭이 원인’, ‘감소분 전부가 GEMM’, ‘교재와 GPU 세대가 달라 생긴 결과’라고 단정하지 않습니다.

## 4. 운영 도입 주장에는 품질 비교가 필요하다

속도만으로 양자화 도입을 권하지 않습니다. 실제 사용 과제를 대표하는 고정 입력과 정답·평가 기준을 준비해 BF16·FP8을 비교합니다. 예를 들어 한국어 사실 질의, 요약의 핵심 사실 보존, 구조화 출력의 스키마 준수를 나눠 볼 수 있습니다. 항목 수와 통과 기준은 결과를 보기 전에 정합니다.

단순히 문장이 달라졌다는 이유로 품질 저하로 세지 않습니다. 가능한 항목은 정답·스키마로 판정하고, 주관 평가가 필요하면 모델 이름을 가린 상태로 같은 기준을 적용합니다. 작은 표본은 탐색 결과로 표시합니다. 품질을 평가하지 않은 현재 글은 성능 분석으로 범위를 한정했습니다.

## 5. 지금 늘리지 않아도 되는 범위

더 큰 모델, AWQ·GPTQ·FP4, Multi-LoRA, 여러 라우터, 다중 GPU는 독립된 주제가 됩니다. 현재 글의 질문에 답하려고 모두 추가할 필요는 없습니다. 우선순위는 **원본 집계 복구 → KV 여유 2×2 실험 → 원인별 프로파일링 → 운영 목적의 품질 평가**입니다. 시간 여유가 작으면 첫 단계와 현재 글의 정확한 한계 표기로 마무리합니다.
