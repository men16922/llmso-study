# 통합 메모리 vs VRAM 설계 스냅샷 — 메모리도 크고 대역폭도 높은데 왜 서빙에서는 지는가

작성 2026-09-01 · **착수 시점 미정** · 실행 트리거는 §7 · 롤링 포인터는 [`docs/NEXT_PLAN.md`](../NEXT_PLAN.md) Priority 2

실험 ID는 **G**로 시작합니다 (2주차 B · 3주차 C · 4주차 E · 5주차 F와 구분).

## 0. 왜 이걸 5주차 과제로 안 넣는가 (판단 기록)

2026-09-01 세션에서 "이걸 과제로 다루면 어떤가"를 검토하고 **미루기로** 결정했습니다. 근거 셋:

1. **통제 변수가 완전히 무너집니다.** 하드웨어·런타임·커널·양자화 포맷·스케줄러가 동시에 바뀝니다. 그런데 5주차 축이 하필 *"원인 귀속"* 이라 **정확히 반대 방향**입니다. 2주차 B1부터 지켜온 "실행 경로 고정, 한 번에 하나만"도 깨집니다.
2. **CH9·CH10 범위 밖입니다.** 과제는 챕터 대응이고 하드웨어 플랫폼 비교는 두 장 어디에도 없습니다.
3. **시간.** 마감까지 5일인데 F1(주인공)·F2(CH10 공식 도전과제)를 깎는 교환이 됩니다.

**단, 비용은 처음 추정보다 훨씬 쌉니다** — `labs/wsl2-vllm-baseline/benchmark.py`가 **OpenAI 호환 + `--base-url` 인자**라 맥 엔드포인트에 **코드 수정 0으로** 그대로 붙습니다(`benchmark.py:560`, `/v1/models` 자동 탐색은 `:129`). 측정 하네스를 새로 만들 필요가 없다는 뜻입니다. 그래서 폐기가 아니라 **보류**입니다.

## 1. 질문 — 속도가 아니라 능력을 묻는다

플랫폼 간 **속도 순위**("어느 쪽이 빠른가")는 교란 때문에 죽습니다. 무엇 때문에 빠른지 귀속을 못 하니까요. 대신 **능력 질문**은 교란을 견딥니다:

> **12GB VRAM에서 아예 못 올리는 모델을 48GB 통합 메모리에서는 올린다. 그런데 동시 요청이 붙으면 그 우위가 어디서 뒤집히는가?**

훅은 숫자가 뻔하지 않다는 데 있습니다 — **맥이 메모리도 3배 크고 대역폭도 더 높은데 서빙에서는 진다.** 답이 ① 프리필의 연산(텐서 코어)과 ② **연속 배칭이라는 소프트웨어**에 있다는 게, 이 스터디 5주치 내용과 그대로 이어집니다.

### 기존 글과의 연결

- **4주차 결론**(*"조건은 한 스텝의 토큰 예산에 여유가 있는가"*)의 다음 칸입니다. 여기서는 **예산의 총량 자체가 3배 다른** 두 저울을 놓고 같은 질문을 합니다.
- **`docs/NEXT_PLAN.md`의 이월분 "배칭 4종 표의 `없음`·`static` 칸"을 메울 수 있습니다.** llama.cpp의 `--parallel N`은 컨텍스트를 **N등분한 고정 슬롯**으로 나누는 것으로 보이는데(§4 G2에서 확인), 사실이면 그게 바로 표의 `static` 칸입니다. PagedAttention과의 대비가 실물로 잡힙니다.

## 2. 두 저울 (실측 / 공칭 구분)

| | RTX 4080 Laptop (WSL2) | Apple M4 Max (이 맥) |
|---|---|---|
| 모델용 메모리 | **12,282 MiB** (실측, 4주차 기동 로그) | 48GB 통합 (실측 `system_profiler`, 2026-09-01) |
| GPU 가용분 | 12GB 전부 | **~36GB 추정** — `iogpu.wired_limit_mb=0`(기본값) 확인. **실제 상한은 착수 시 확인** |

| 연산 | 텐서 코어 有 | 텐서 코어 상당물 없음 |
| 코어 | — | GPU 40 · CPU 16(12P+4E) (실측) |

| 프로파일러 | Nsight Systems/Compute | **없음** (Instruments는 커널 귀속이 안 됨) |

★ **대역폭 두 값은 공칭입니다.** 결론의 근거로 쓰려면 착수 시 실측하거나, 공칭임을 글에 명시해야 합니다.

## 3. ★ 교란 통제 — 이 실험의 가장 약한 고리

한 번에 바뀌는 변수가 다섯 개(하드웨어·런타임·커널·양자화 포맷·스케줄러)입니다. **그래서 절대 수치의 플랫폼 간 직접 비교를 결론으로 쓰지 않습니다.** 대신 교란을 견디는 세 가지만 씁니다:

1. **능력 판정** — "올라가는가 / 안 올라가는가"는 이분법이라 교란과 무관합니다.
2. **곡선의 모양** — 동시성을 올렸을 때 처리량이 **오르는가 평평해지는가**. 모양은 배칭 구현의 성질이라 하드웨어 차이로 설명되지 않습니다. **이게 주인공입니다.**
3. **플랫폼 *내부* 비율** — 같은 플랫폼 안에서 TTFT 대비 ITL이 어떻게 갈리는지. 비율은 절대 성능이 약분되므로 "프리필은 연산 바운드, 디코드는 대역폭 바운드"를 검증할 수 있습니다.

**맞출 수 있는 것은 맞춥니다**: 같은 모델 계열 · 같은 양자화 비트폭(4bit) · 같은 프롬프트 세트 · **같은 출력 토큰 수**(C1에서 정렬을 빠뜨려 2.5배 왜곡됐던 전례 — `docs/NEXT_PLAN.md` Priority 3). 출력 길이가 안 맞으면 처리량 비교는 그 자리에서 무의미해집니다.

## 4. 실험 설계 (G 시리즈)

### G1 — 천장: 무엇이 어디에 올라가는가

- **질문**: 12GB와 48GB의 능력 경계는 실제로 어디인가.
- **방법**: 모델 크기를 올리며 **기동 성공/실패**만 기록. 4bit 양자화 기준으로 1.5B → 7B → 14B → 32B.
- **Done**: 각 플랫폼의 최대 모델과, **기동 로그의 KV 예산**(vLLM은 `Maximum concurrency`, llama.cpp는 `n_ctx`/슬롯)이 표로 남는다.
- 주의: "올라간다"와 "쓸 만하다"는 다릅니다. 기동만 되고 c=1에서도 느리면 그 사실까지 기록.

### G2 — 동시성 스케일링의 모양 ★ 주인공

- **질문**: 동시성을 올리면 두 곡선의 **모양**이 어떻게 갈리는가. 교차점이 있는가, 있다면 어디인가.
- **팔**: **양쪽에 다 올라가는 모델 하나**로 고정 — `Qwen2.5-1.5B-Instruct`. **4주차 baseline과 같은 모델이라 기존 저울·프롬프트·출력 길이를 그대로 재사용**할 수 있습니다.
- **축**: c = 1, 4, 8, 16, 32 (`benchmark.py --concurrency`). 워크로드는 4주차의 `prefill`·`decode` 두 종.
- **예측**: vLLM은 오르다 포화, llama.cpp/MLX는 일찍 평평해진다. **평평해지는 지점이 곧 배칭 구현의 한계**.
- ★ **여기서 `--parallel N`의 KV 분할 방식을 확인합니다.** 컨텍스트를 N등분해 고정 슬롯을 잡는다면, 그게 배칭 4종 표의 `static` 칸이고 PagedAttention과의 대비가 실물로 잡힙니다.
- **Done**: 두 곡선이 한 그림에(`tools/make_figures.py`), 교차 여부에 대한 판정 한 줄.

### G3 — 프리필/디코드 분해: 연산이 부족한가 대역폭이 부족한가

- **질문**: 맥이 뒤진다면 **어디서** 뒤지는가. 프리필(연산 바운드)인가 디코드(대역폭 바운드)인가.
- **방법**: G2 데이터에서 **TTFT**와 **ITL**을 분리해, 플랫폼 **내부 비율**로 비교.
- **예측**: 대역폭은 맥이 더 높으므로 **ITL 격차 < TTFT 격차**여야 합니다. 이게 나오면 "텐서 코어의 부재"가 설명력을 얻고, 안 나오면 원인이 소프트웨어 쪽이라는 뜻 — **어느 쪽이 나와도 결과입니다.**
- 5주차 F1의 논리(*"처리량은 올랐는데 커널은 그대로"*)와 **같은 모양의 질문**이라 글이 이어집니다.

### G4 — 큰 모델 단독 (선택, 잘라내기 1순위)

- 32B 4bit를 맥에서 c=1로. 4080에서는 **기동 불가**가 결과.
- 수직 확장의 천장을 보여주는 그림 하나. 시간 없으면 자릅니다.

## 5. 스택 선택 — llama.cpp 우선, MLX는 여유 있으면

| | 장점 | 단점 |
|---|---|---|
| **llama.cpp** (`llama-server`) ★ | **연속 배칭 있음**(`--parallel`) · `-c`/슬롯을 직접 통제 · OpenAI 호환 · GGUF 광범위 | Metal 활용도가 MLX보다 낮을 수 있음 |
| MLX (`mlx_lm.server`) | 애플 자체 프레임워크, Metal 활용 최적 | 배칭 통제가 제한적 |
| ollama | **이미 설치됨**(`/usr/local/bin/ollama`) | 배칭 설정이 불투명(`OLLAMA_NUM_PARALLEL`) — 통제 실험에 부적합 |

**결론: 측정은 `llama-server`로.** 배칭 슬롯을 명시적으로 통제할 수 있어야 G2가 성립합니다. **ollama는 ⓪ 스모크용**(엔드포인트 연결 확인)으로만 씁니다. MLX는 G2가 닫힌 뒤 여유가 있으면 세 번째 팔로.

## 7. 실행 트리거 — 언제 꺼내는가

**둘 중 먼저 오는 것:**

- **(A) 5주차 ⑦(링크 공유)이 닫힌 뒤**, 별도 블로그 글로. 챕터 제약도 마감도 없습니다. 콘텐츠 정책상 *"소화해서 자기 언어로 가공하는 것(블로그 등)은 권장"* (`CLAUDE.md`).
- **(B) 6주차 비상 대안.** **AWS GPU 쿼터가 `0`인 채로 6주차 EKS가 막히면** 이걸 꺼냅니다. 클라우드가 전혀 필요 없는 주제라 대체재로 성립합니다. 판단 시점은 **2026-09-06 스터디 모임 직후**.

## 8. 중단 기준 (kill switch)

- ⓪-2가 막히면(하네스 재사용 불가) — **중단.** 벤치 클라이언트를 새로 쓰는 순간 비용이 이 계획의 전제를 벗어납니다.
- ⓪-5에서 출력 길이 정렬이 안 되면 — G2·G3 폐기, **G1(능력 판정)만** 남기고 짧은 글로 축소.
- llama.cpp 설치·모델 확보에 **2시간** 초과 — 중단하고 트리거 (A)/(B) 재판정.
- **5주차 산출물에 조금이라도 영향이 가면 즉시 중단.** 과제가 우선입니다.

## 10. 하지 않을 것 (명시)

- ❌ **"어느 쪽이 빠른가" 순위 매기기.** 교란 때문에 성립하지 않습니다.
- ❌ **커널 수준 귀속.** 맥에는 Nsight Compute 상당물이 없습니다. 5주차 F2를 맥에서 재현하려는 시도 금지 — **원리상 불가**이고, 이 사실 자체가 5주차 「한계」 절에 한 문단으로 들어갑니다.
- ❌ **절대 수치의 플랫폼 간 직접 비교를 결론 문장으로 쓰기.** §3의 세 가지(능력 판정 · 곡선 모양 · 플랫폼 내부 비율)만 결론 근거가 됩니다.
- ❌ WSL2 랩톱 설정 변경. 4주차·5주차 저울을 건드리지 않습니다.
