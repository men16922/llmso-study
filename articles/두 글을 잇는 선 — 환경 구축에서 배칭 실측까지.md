# 두 글을 잇는 선 — 환경 구축에서 배칭 실측까지

> **한 줄 요약**: 1주차 글([WSL2를 로컬 GPU Kubernetes 개발 환경으로 사용하기](./WSL2%EB%A5%BC%20%EB%A1%9C%EC%BB%AC%20GPU%20Kubernetes%20%EA%B0%9C%EB%B0%9C%20%ED%99%98%EA%B2%BD%EC%9C%BC%EB%A1%9C%20%EC%82%AC%EC%9A%A9%ED%95%98%EA%B8%B0.md))은 **계측 가능한 GPU 환경을 만든 기록**이고, 2주차 글([Continuous Batching이 처리량을 높이는 방식](./Continuous%20Batching%EC%9D%B4%20%EC%B2%98%EB%A6%AC%EB%9F%89%EC%9D%84%20%EB%86%92%EC%9D%B4%EB%8A%94%20%EB%B0%A9%EC%8B%9D.md))은 **그 계측기로 실제 서빙 시스템을 잰 기록**이다. 둘은 같은 노트북, 같은 k3s, 같은 Prometheus 위에서 이어진다.

---

## 왜 두 글인가

한 문장으로 놓으면 이렇다.

> **1주차**: GPU가 컨테이너와 쿠버네티스에서 **보이는가**
> **2주차**: 그 GPU가 실제로 **얼마나 일하는가**

1주차 글의 마지막 장은 `gpu-burn`으로 부하를 걸어 사용률이 100%로 붙는 것을 확인하고 끝난다. 거기서 멈추면 "GPU가 돌아간다"까지다. 2주차 글은 그 위에 vLLM을 올리고 **같은 GPU에서 처리량이 23배 벌어지는 구간**을 찾는다. 하드웨어는 그대로고 바뀐 것은 정수 하나(`--max-num-seqs`)다.

즉 1주차는 **인프라 문서**, 2주차는 **성능 문서**다. 그런데 둘은 단순히 순서대로 놓인 게 아니라, **1주차에서 부딪힌 한계가 2주차의 측정 방법을 결정했다.** 그게 이 문서에서 가장 하고 싶은 이야기다.

---

## 1. 1주차에 만든 것이 2주차에서 어디에 쓰였나

<details>
<summary><b>구성요소별 대응표</b></summary>

| 1주차에서 세운 것 | 2주차에서 쓰인 곳 |
|---|---|
| K3s + NVIDIA Device Plugin (`nvidia.com/gpu: 1`) | vLLM 파드가 GPU 1장을 요청. 슬롯 값을 바꿀 때마다 `strategy: Recreate`로 재배포 |
| RuntimeClass `nvidia` | vLLM 파드가 GPU를 보려면 필수. 1주차 7.3에서 `kubectl patch`로 붙인 그 설정 |
| kube-prometheus-stack + ServiceMonitor | 2주차 5-8의 `vllm:num_requests_running`/`_waiting` 수집 경로. **증빙 캡처 3장이 전부 여기서 나왔다** |
| `port-forward` 우회 (1주차 7.7) | Windows에서 NodePort가 안 열리는 문제. 2주차 재현 절차의 8000·30001·30002 포워딩이 전부 이것 |
| WSL 세션 유지 (1주차 7.5) | 2주차 실습 절차 `0-1`. 이걸 빠뜨리면 측정 중 파드가 `Completed`로 떨어진다 |
| `mount --make-rshared /` (1주차 7.6) | node-exporter가 떠 있어야 Prometheus 스택이 온전하다 |
| PVC `huggingface-cache` | 모델 가중치 재다운로드 방지. 슬롯 스윕에서 롤아웃을 10번 돌렸는데 다운로드는 한 번뿐 |

</details>

**정리하면 2주차 글은 새로 만든 인프라가 거의 없다.** 1주차에서 세운 것 위에 vLLM 매니페스트 하나를 올렸을 뿐이다. 환경 구축 글을 따로 써 둔 값이 여기서 나온다.

## 2. 1주차의 한계가 2주차의 방법을 정했다 ★

이 문서의 핵심이다. 1주차 글에서 **못 한 것**들이 2주차의 측정 설계를 바꿨다.

<details>
<summary><b>① DCGM 프로파일링 메트릭 부재 → 측정 지표를 GPU가 아니라 서버로</b></summary>

1주차 5장에서 확인한 것: WSL2에서는 `DCGM_FI_PROF_*` 계열이 나오지 않는다. Grafana 12239 대시보드의 **`Tensor Core Utilization` 패널이 통째로 비어 있었다.**

여기서 2주차 측정 설계가 갈렸다. **GPU 사용률로는 배칭 효과를 잴 수 없다.**

- `DCGM_FI_DEV_GPU_UTIL`은 `slots=1`이든 `slots=64`든 부하를 걸면 똑같이 **100%**를 찍는다. "일하고 있음"만 알려주지 "몇 개를 동시에 처리하고 있는가"는 알려주지 않는다.
- 그런데 배칭의 효과는 정확히 그 "몇 개를 동시에"에 있다. 2주차 글 1절의 문제 제기 — *"사용률이 100%인데도 처리량이 더 오른다면, 100%라는 숫자가 재고 있는 것은 '일하고 있음'이지 '꽉 찼음'이 아니다"* — 가 바로 이것이다.

그래서 2주차는 **GPU 계층을 건너뛰고 서빙 엔진 계층의 메트릭**으로 갔다.

| 층 | 지표 | 배칭을 재는 데 쓸 수 있나 |
|---|---|---|
| GPU (DCGM) | `DCGM_FI_DEV_GPU_UTIL` | ❌ 어떤 슬롯 값이든 100% |
| GPU (DCGM) | `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | ❌ **WSL2에서 미노출** (1주차 5장) |
| 서빙 엔진 (vLLM) | `vllm:num_requests_running` / `_waiting` | ✅ **슬롯 천장과 큐가 그대로 보인다** |
| 클라이언트 | TTFT p95 · ITL · goodput | ✅ 사용자가 겪는 값 |

1주차의 빈 패널이 없었다면 2주차는 GPU 사용률 그래프를 붙이고 "포화했다"로 끝났을 것이다. **막힌 길이 더 나은 길을 고르게 했다.**

</details>

<details>
<summary><b>② TGP 전력 상한 → 2주차 글의 "한계 2"</b></summary>

1주차 7.4에서 확인한 것: 이 랩탑은 **열 스로틀링보다 105W 전력 상한에 먼저 걸린다.** 처리량이 17.1 → 17.0 TFLOPS로 거의 유지되는 동안 클럭만 1665 → 1530MHz로 내려갔다. 그리고 `power.limit`이 105W → 84W → `[N/A]`로 오락가락하는 것도 관측됐다.

2주차 측정에서는 `nvidia-smi --query-gpu=power.limit`이 아예 `[N/A]`를 반환했다. 그래서 2주차 글은 한계 2에 이렇게 적었다 — **절대값은 이 기기 고유값으로 보고, 비교는 열 간 상대값으로만 유효하다.**

1주차에 전력 거동을 확인해 두지 않았다면 이 `[N/A]`를 그냥 넘겼을 것이다. 랩탑 GPU의 절대 성능 수치를 다른 환경과 비교하면 안 되는 이유를 1주차가 이미 보여줬다.

</details>

<details>
<summary><b>③ WSL 유휴 poweroff → 2주차 측정을 실제로 한 번 끊었다</b></summary>

1주차 7.5의 증상: 몇 분만 비워도 파드가 전부 `Completed`/`Error`로 떨어지고 `nvidia.com/gpu`가 0이 된다. 해결은 `wsl -d Ubuntu -u root -- sleep infinity` 세션을 붙잡아두는 것뿐이었다(`vmIdleTimeout=-1`은 실패).

2주차 측정 중 이 세션이 죽으면서 **`slots=64` decode 구간에서 스윕이 끊겼다.** 파드가 `Unknown`/`Completed`로 무더기로 떨어졌고, 잔재 파드가 GPU를 붙들어 새 파드가 `Insufficient nvidia.com/gpu`로 Pending에 걸렸다.

복구는 잔재 파드를 강제 삭제하는 것이었고, 이후 남은 2건을 다시 돌려 전량 확보했다. 1주차에 원인을 특정해 두지 않았다면 "왜 갑자기 GPU가 사라졌지"에서 한참 헤맸을 것이다.

> 2주차 글의 재현 절차가 `0-1`(WSL 세션 붙잡기)로 시작하는 이유가 이것이다.

</details>

<details>
<summary><b>④ 재현 못 한 것들 → 4~6주차로 이월</b></summary>

1주차 7.2에 적어둔 목록: MIG, NVIDIA GPU Operator, NVLink/NCCL 멀티 GPU, HAMi, DCGM 프로파일링, PCIe 대역폭.

2주차 글의 한계 5(**단일 GPU·단일 레플리카**)가 같은 제약의 연장이다. 라우팅·오토스케일·멀티 노드는 GPU가 한 장인 이상 잴 수 없다. 예습 노트 §2가 다루는 *concurrency target ↔ batch size 정합*도 레플리카가 여럿이어야 실측이 되므로, 이번엔 개념 대응까지만 하고 넘어갔다.

이 항목들이 6주차 EKS 실습(AWS GPU 쿼터 신청이 선행 조건)으로 넘어간다.

</details>

## 3. 2주차 스터디(CH3·CH4)와 글은 어떻게 대응하나

<details>
<summary><b>교재 장별 ↔ 글의 절 대응표</b></summary>

| 교재 | 예습 노트 | 2주차 글에서 |
|---|---|---|
| CH3 배칭 3종 (static / dynamic / continuous, p.188) | §1 | **2절** 표에 "배칭 없음"을 더해 4종으로 정리. 실측은 양 끝(`slots=1` ≈ 배칭 없음, `slots=64` = continuous)만 |
| CH3 *"배치 크기는 지연과 처리량을 맞바꾼다"* (p.190) | §1 「1주차 질문의 답」 | **5-5 파레토 표**가 그 트레이드오프의 가격표. "SLO를 지키며 낼 수 있는 최대 처리량 2,626.7 tok/s"가 답 |
| CH3 *"여러 배치 크기에 걸쳐 성능을 시험하라"* (p.190) | §1 | **B1 스윕 그 자체**. 슬롯 1/16/64 × 동시성 7단계 |
| CH3 concurrency target ↔ batch size 정합 (p.190) | §2 | **6절 ①** — 슬롯은 튜닝 노브가 아니라 용량 정의. **7절 확장성** — KV cache가 먼저 천장을 정한다 |
| CH4 지표 TTFT·ITL/TPOT (p.37) | §6 | **5-2**(TTFT) · **5-4**(ITL). "비용은 ITL이 아니라 TTFT로 청구된다"가 이 두 절의 결론 |
| CH4 *"평균이 아니라 백분위"* (p.39) | §6 | 전 표가 **p95** 기준. goodput도 SLO 충족 비율 |
| CH4 지연 공식 `E2E = TTFT + ITL×(N−1)` | §6 | **5-6 지연 공식 검증**. 잔차가 큐를 안 보여준 이유까지 |
| CH4 성능 측정 모범 사례 9가지 | §6 | 시나리오 허브 문서의 대조표. 이번 글이 덮은 것은 1·2·3·5·6·7번 |

</details>

<details>
<summary><b>예습 노트가 남긴 질문에 글이 답한 것</b></summary>

예습 노트 §1은 1주차에서 넘어온 질문을 이렇게 적어 뒀다.

> **배칭이 decode의 memory bound를 완화한다면 배치를 무한정 키우면 왜 안 되나?**

노트의 답은 교재를 인용한 개념 수준이었다 — *"어떤 임계값을 넘으면 터져서가 아니라 애초에 트레이드오프이기 때문"*. 2주차 글은 이 답을 **두 방향에서 숫자로 채웠다.**

1. **트레이드오프의 가격표** — 5-5 파레토. 처리량을 얼마나 사면 지연을 얼마나 파는지가 행 단위로 나온다.
2. **그런데 트레이드오프가 아닌 구간도 있다** — 파레토 경계가 전부 `slots=64`다. 슬롯을 16에서 64로 올리는 것은 잃는 게 없다. **트레이드오프는 슬롯이 아니라 그 위에서 동시성을 얼마나 밀어 넣느냐에서 생긴다.**

②는 예습 노트에 없던 내용이고, 실측이 아니었으면 나오지 않았을 구분이다. 다만 무한정 키울 수 없는 이유는 따로 있었다 — **KV cache가 먼저 천장을 정한다**(7절 확장성). `slots=64`로 띄웠는데 vLLM이 보고한 실제 수용량은 59.50x였다.

</details>

## 한 장으로 요약하면

```
[1주차] Windows GPU  →  WSL2  →  Docker  →  K3s(nvidia.com/gpu)  →  DCGM → Prometheus/Grafana
                                                    │                        │
                                                    │  "GPU가 보인다"          │  "GPU가 100%다"
                                                    ▼                        ▼
[2주차]                                      vLLM 파드 배포          ← 여기서 막힌다.
                                                    │                  사용률로는 배칭을 못 잰다
                                                    ▼                        │
                                   --max-num-seqs 1 / 16 / 64 스윕            │
                                                    │                        ▼
                                                    └──────────→  vllm:num_requests_running / _waiting
                                                                  TTFT p95 · ITL · goodput
                                                                        │
                                                                        ▼
                                                       "슬롯이 천장을 정하고,
                                                        초과분은 전부 큐로 간다"
```

1주차가 만든 것은 GPU 환경이 아니라 **관측 경로**다. 2주차는 그 경로의 마지막 한 칸(GPU 사용률)이 쓸모없다는 것을 확인하고, 한 층 위(서빙 엔진)에서 답을 찾았다.
