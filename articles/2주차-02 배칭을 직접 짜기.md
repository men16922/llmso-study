## ★ 먼저 알아야 할 것 — 이 서버는 동시 요청을 배칭하지 못합니다

C1을 설계하다 코드에서 발견했고, **강의 노트도 같은 것을 관측했습니다.**

> `[실습4]` (참고) vllm 2개 이상 동시 요청 시 현재 코드 상태(continuous batching 불가)로는 **순차 처리됨**. 하나의 실행 배치에 섞으려면 → `vllm.AsyncLLMEngine`(비동기 엔진) 설정 필요.

> *"앞 실습에서 vLLM 동시 요청 테스트에서, **Uvicorn이 단일 이벤트 루프로 동작하고 `generate_vllm`이 await 없는 동기 호출**이라 두 요청이 진짜 동시에 처리되지 못하고 순차 처리됐습니다."*

원인은 `main.py`에 그대로 보입니다.

| 줄 | 핸들러 | 안에서 하는 일 |
|---|---|---|
| `main.py:63` | `async def basic_generate` | `llm.basic_generate(...)` — **동기 블로킹** |
| `main.py:69` | `async def generate` | `llm.generate(...)` — **동기 블로킹** (게다가 `time.sleep(0.1)` 루프) |
| `main.py:74` | `async def generate_vllm` | `llm.generate_vllm(...)` — **동기 블로킹** |
| `main.py:49` | `async def generate_stream` | `async for` — 유일하게 진짜 비동기 |

FastAPI에서 `async def` 핸들러 안의 블로킹 호출은 **이벤트 루프 전체를 멈춥니다.** 그래서 클라이언트가 동시성 32로 때려도 서버는 하나씩 처리합니다.

### 이게 실험 설계를 바꿉니다

**교재 서버의 배칭 축은 "동시 요청 수"가 아니라 "요청당 프롬프트 수"입니다.** `[실습2]`가 정확히 그것을 보여줍니다 — 프롬프트 5개를 **한 요청에** 담아 보내니 `batch_size=4`가 앞의 4개를 묶고(`torch.Size([4, 5])`), 남은 1개가 다음 배치로 갔습니다.

> `/generate`는 자기 요청 안의 프롬프트만 배칭합니다. **요청 간 배칭은 구조적으로 불가능**합니다 — 다른 요청이 도착하려면 이벤트 루프가 살아 있어야 하는데, 지금 그 루프를 자기가 막고 있으니까요.

그래서 `benchmark.py`에 `--prompts-per-request`를 넣었습니다. 동시성 축과 프롬프트 축을 **분리해서** 재야 두 현상이 섞이지 않습니다.

---

## 이 실험이 성립하는 이유

`single_model_llm_serving`에는 **배칭 네 방식이 한 서버 안에** 들어 있습니다. 같은 모델(`facebook/opt-125m`), 같은 프로세스, 같은 GPU — 통제가 완벽합니다.

| 엔드포인트 | 구현 위치 | 배칭 성격 | 동시 요청 |
|---|---|---|---|
| `/basic_generate` | `llm.py` `basic_generate()` — WorkloadManager 우회 | **배칭 없음** | ✗ 직렬 |
| `/generate` | `llm.py` `generate()` — `while not _is_batch_finished` | **static** | ✗ 직렬 |
| `/generate_stream` | `requests_processing_loop()` — 슬롯 비는 대로 채움 | **naive continuous** | ✅ |
| `/generate_vllm` | 인프로세스 vLLM | **continuous (vLLM)** | ✗ 직렬 |

그리고 `workload_manager.py:23`의 `self.batch_size = 4`가 [01](./2%EC%A3%BC%EC%B0%A8-01%20%EB%B0%B0%EC%B9%98%20%EC%8A%AC%EB%A1%AF%EA%B3%BC%20%ED%81%90.md)의 `max-num-seqs`에 대응합니다.

---

## 가설

1. **`--prompts-per-request`를 늘리면 `/generate`의 처리량이 오르다가 `batch_size=4`의 배수 경계에서 계단을 그린다.** 5개면 4+1 두 배치이므로 4개일 때보다 요청당 시간이 거의 두 배.
2. **동시 요청 수를 늘려도 `/basic_generate`·`/generate`·`/generate_vllm`은 처리량이 평평하다.** 이벤트 루프가 막혀서다. `/generate_stream`만 오른다.
3. **핸들러를 `async def` → `def`로 한 글자 고치면** 셋 다 동시성이 살아난다. FastAPI가 threadpool로 돌리기 때문.
4. static → continuous 전환이 버는 것보다, **vLLM까지의 남은 격차가 더 크다.** 전자는 스케줄링 설계, 후자는 PagedAttention·커널·메모리 관리의 몫.

## C1-1. 공정성 정렬 ★ 이걸 안 하면 비교가 무의미합니다

**세 엔드포인트의 출력 토큰 수가 서로 다릅니다.**

| 위치 | 현재 값 | 영향 |
|---|---|---|
| `llm/llm.py:17` | `self.max_tokens = 20` | `/generate_stream`, `/generate_vllm` |
| `llm/model_worker.py:48` | `max_new_tokens=50` | `/basic_generate`, `/generate` |

`/generate`만 50토큰을 만들고 나머지는 20토큰입니다. **이 상태로 처리량을 비교하면 2.5배 왜곡**됩니다.

```bash
sed -i 's/max_new_tokens=50/max_new_tokens=20/' llm/model_worker.py
grep -n "max_new_tokens" llm/model_worker.py    # 확인
```

> 이 불일치를 발견한 것 자체가 글감입니다 — 교재 CH4 벤치마킹 모범 사례의 *"한 번에 한 노브만"*, *"실험의 일관성 유지"* 가 정확히 이 이야기입니다.

## C1-2. 벤치마크 어댑터 — **이미 만들어져 있습니다**

`benchmark.py`에 `--api book` 모드가 들어가 있습니다.

```bash
python3 benchmark.py --api book --endpoint /generate --prompts-per-request 4 ...
```

| 엔드포인트 | 요청 | 응답 | TTFT |
|---|---|---|---|
| `/basic_generate` | `{"prompt": "..."}` | `{"generated_text": "..."}` | ✗ |
| `/generate` | `{"prompts": [...]}` | `{"generated_texts": [...]}` | ✗ |
| `/generate_stream` | `{"prompt": "..."}` | SSE `data: {"token": " a", ...}` | ✅ |
| `/generate_vllm` | `{"prompts": [...]}` | `{"generated_texts": [...]}` | ✗ |

코드를 읽으며 찾은 **함정 넷**이 이미 처리돼 있습니다. 결과를 해석할 때 알아둬야 합니다.

1. **`/generate`·`/basic_generate`는 프롬프트를 그대로 되돌려줍니다.** `ModelWorker.generate()`가 `batch_decode(outputs)`를 반환하는데 `outputs`는 `[프롬프트 토큰 + 생성 토큰]` 전체입니다. → 어댑터가 **응답 개수만큼** 프롬프트 몫을 빼고 셉니다.
2. **비스트리밍은 TTFT가 정의되지 않습니다.** 그런데 goodput 계산이 TTFT 없는 결과를 전부 SLO 위반으로 세면 0%가 나옵니다. → TTFT가 없으면 **E2E SLO만으로** 판정합니다.
3. **`usage`가 없어** 출력 토큰은 공백 분리로 셉니다. 네 엔드포인트가 **모두 같은 방식**이라 상대 비교는 유효하지만, vLLM 서버(`--api openai`)의 tok/s와 절대값을 직접 비교하면 안 됩니다.
4. **응답 여러 개를 이어 붙여 세면 안 됩니다.** 앞 응답의 마지막 단어와 다음 응답의 첫 단어가 붙어 하나로 세어집니다. → **개별로 세서 더합니다.**

> 넷 다 `test_benchmark.py`의 `BookApiTest`가 검증합니다(`make check`에 포함). 특히 `test_all_four_endpoints_count_the_same_way`와 `test_prompt_echo_subtracted_once_per_response`가 계수법이 어긋나지 않게 지킵니다.

## C1-A. 프롬프트 축 — 교재가 말하는 진짜 배칭 ★

### 실행

동시성은 **1로 고정**하고 요청당 프롬프트 수만 바꿉니다. 이벤트 루프 문제를 실험에서 제거하기 위해서입니다.

```bash
cd ~/llm-model-inference/ch03/single_model_llm_serving
BENCH=~/"Hands-On LLM Serving and Optimization Study"/labs/wsl2-vllm-baseline/benchmark.py
mkdir -p results

python main.py > /tmp/book-server.log 2>&1 &
until curl -sf -X POST localhost:8000/basic_generate \
      -H 'Content-Type: application/json' -d '{"prompt":"hi"}' >/dev/null; do sleep 3; done

for N in 1 2 4 5 8 16; do
  for EP in generate generate_vllm; do
    python3 "$BENCH" --api book --endpoint /$EP \
      --scenarios short --concurrency 1 --requests-per-level 20 \
      --prompts-per-request $N \
      --output results/c1a-$EP-n$N.json
  done
done
```

`/basic_generate`와 `/generate_stream`은 프롬프트를 하나만 받으므로 이 축이 없습니다 — 그게 결과입니다.

### 관측 — 채울 표

| 프롬프트/요청 | `/generate` 처리량 | `/generate` 요청당 E2E | `/generate_vllm` 처리량 | `/generate_vllm` 요청당 E2E |
|---|---|---|---|---|
| 1 | | | | |
| 2 | | | | |
| 4 | | | | |
| **5** | | | | |
| 8 | | | | |
| 16 | | | | |

서버 로그에서 배치 모양도 함께 기록하세요 — `[실습2]`가 보여준 그 로그입니다.

```bash
grep -E "Sending batch to worker|Batch input shape" /tmp/book-server.log | tail -20
# 기대: torch.Size([4, N]) 다음에 torch.Size([1, N])
```

### 판단 기준

- ✅ **가설 1대로면**: 프롬프트 4개까지는 요청당 E2E가 거의 일정하고(한 배치), **5개에서 계단이 생깁니다**(4+1 두 배치). 8개는 두 배치, 16개는 네 배치.
- ✅ **`/generate_vllm`은 계단이 없어야 합니다.** vLLM이 자체 스케줄링을 하므로 `batch_size=4`와 무관합니다. **이 대비가 static과 continuous의 차이를 가장 선명하게 보여줍니다.**
- ⚠️ **패딩 낭비**: `ModelWorker.generate()`가 `padding=True`로 배치를 묶으므로, 길이가 다른 프롬프트가 섞이면 **가장 긴 것에 맞춰 패딩**됩니다. `--unique-prefix`를 켜면 프롬프트 앞에 UUID가 붙어 길이가 균일해지므로, **켜고 끄고 각각** 재보면 패딩 비용이 보입니다.

## C1-B. 이벤트 루프 블로킹 ★ 이 편의 핵심

### 실행 — 수정 전

동시성만 올립니다. 프롬프트는 요청당 1개로 고정.

```bash
for EP in basic_generate generate generate_stream generate_vllm; do
  python3 "$BENCH" --api book --endpoint /$EP \
    --scenarios short --concurrency 1,2,4,8,16,32 \
    --requests-per-level 50 \
    --output results/c1b-before-$EP.json
done
```

### 실행 — 한 글자 수정 후

```bash
# async def → def. FastAPI가 threadpool에서 돌려 이벤트 루프를 막지 않는다
sed -i 's/^async def basic_generate/def basic_generate/;
        s/^async def generate(/def generate(/;
        s/^async def generate_vllm/def generate_vllm/' main.py
grep -n "^async def\|^def " main.py     # generate_stream만 async로 남아야 정상

pkill -f "python main.py"; sleep 3
python main.py > /tmp/book-server-after.log 2>&1 &
until curl -sf -X POST localhost:8000/basic_generate \
      -H 'Content-Type: application/json' -d '{"prompt":"hi"}' >/dev/null; do sleep 3; done

for EP in basic_generate generate generate_stream generate_vllm; do
  python3 "$BENCH" --api book --endpoint /$EP \
    --scenarios short --concurrency 1,2,4,8,16,32 \
    --requests-per-level 50 \
    --output results/c1b-after-$EP.json
done
```

> ⚠️ `sed`가 `main.py`의 핸들러 정의만 건드리는지 반드시 눈으로 확인하세요. `generate(` 뒤의 여는 괄호가 `generate_stream`·`generate_vllm`과 구분하는 장치입니다.

### 관측 — 표 생성

```bash
cd ~/"Hands-On LLM Serving and Optimization Study"/labs/wsl2-vllm-baseline
BOOK=~/llm-model-inference/ch03/single_model_llm_serving/results

# 수정 전후를 한 표에 — --delta가 차이·차이% 열을 붙인다
for EP in basic_generate generate generate_vllm generate_stream; do
  echo "### $EP"
  python3 summarize_results.py $BOOK/c1b-before-$EP.json $BOOK/c1b-after-$EP.json \
    --label-regex '(before|after)' --delta --metric output_tok_per_s
done
```

| 동시성 | 수정 전 | 수정 후 | 차이 | 차이 % |
|---|---|---|---|---|
| 1 | | | | |
| 2 | | | | |
| 4 | | | | |
| 8 | | | | |
| 16 | | | | |
| 32 | | | | |

### 판단 기준

- ✅ **가설 2**: 수정 전 `basic_generate`·`generate`·`generate_vllm` 열이 **동시성과 무관하게 평평**해야 합니다. `generate_stream`만 오릅니다.
- ✅ **가설 3**: 수정 후 셋 다 동시성을 따라 오릅니다. 특히 `generate_vllm`은 요청들이 **하나의 vLLM 배치에 섞이기 시작**하므로 가장 크게 뜁니다.
- 💡 **`generate_stream`은 수정 전후가 같아야 합니다** — 원래 진짜 비동기였으니까요. 이게 **대조군**입니다. 여기서도 차이가 나면 측정 노이즈의 크기를 알려주는 지표입니다.
- ⚠️ `generate`가 수정 후에도 안 오르면: `_is_batch_finished` 루프가 자기 request_id만 확인하므로 여전히 요청 간 배칭은 안 됩니다. **threadpool 동시 실행은 되지만 배치는 안 섞이는** 상태 — 그것도 결과입니다.

### 이게 왜 CH3 질문 1번의 답인가

> *"왜 API server, LLM engine, Workload manager, Model executor, Model worker를 굳이 별도 프로세스로 분리하는가? GPU와 CPU 작업을 격리하는 이유는?"*

교재는 `ModelWorker`를 **별도 프로세스**로 띄웁니다(`mp.Process`). GPU 작업을 API 프로세스에서 격리한 것이죠. 그런데 **API 계층에서 동기 호출 한 줄이 그 격리를 무력화합니다** — 워커는 별도 프로세스인데, 그걸 기다리는 쪽이 이벤트 루프를 막으면 격리의 의미가 없습니다.

**"배칭을 구현했는데 처리량이 안 오르면, 배칭이 아니라 API 계층을 의심하라."** 이게 이 편의 한 줄 결론입니다.

### 판단 기준

- ✅ **가설 4**: `generate_stream`까지 오는 데 번 것과, 거기서 `generate_vllm`까지 남은 격차를 비교하세요. 전자가 스케줄링 설계의 몫, 후자가 PagedAttention·커널의 몫입니다.
- ⚠️ **`/generate`가 동시 요청에서 이상한 값을 내면** — 코드상 예견되는 문제입니다. `ModelExecutor.execute_batch()`는 `task_queue.put()` 직후 `result_queue.get()`을 하는데, **동시 호출자 둘이 서로의 결과를 받아갈 수 있습니다**(`model_executor.py:33-46`). 수정 전에는 이벤트 루프가 막혀 이 버그가 드러나지 않았지만, **수정 후에는 드러날 수 있습니다.** 응답이 뒤바뀌거나 예외가 나면 그대로 기록하세요 — *"교재 예제는 단일 요청 데모이지 동시성 안전하지 않다"* 는 것도 CH3 시스템 설계의 결론입니다.
- ⚠️ **`bs=16`이 `bs=4`보다 나쁘면**: `padding=True` 때문입니다. 길이가 다른 요청이 섞이면 패딩 낭비가 커집니다. **vLLM이 토큰 단위로 배칭하는 이유가 바로 이것**이고, [03](./2%EC%A3%BC%EC%B0%A8-03%20dynamic%20batching%EA%B3%BC%20%EA%B7%B8%20%EC%9C%84%EC%9D%98%20%EA%B3%84%EC%B8%B5.md)의 결론으로 이어집니다.

## 이 편의 결론 뼈대

1. 교재 CH3는 배칭과 스트리밍을 직접 구현해 보여준다 — 한 서버에 네 방식이 다 있다
2. 그런데 **동시 요청을 걸면 배칭이 일어나지 않는다.** 원인은 배칭 로직이 아니라 API 계층의 `async def` + 동기 호출
3. 그래서 교재가 시연하는 배칭 축은 **요청당 프롬프트 수**다 (`[실습2]`의 5개 → 4+1)
4. 한 글자를 고치면 동시성이 살아나고, 그제서야 네 방식을 나란히 비교할 수 있다
5. static → continuous가 버는 것보다 **vLLM까지 남은 격차가 크다**. 전자는 스케줄링, 후자는 메모리·커널
6. **컴포넌트를 분리해도 API 계층 한 줄이 그 격리를 무력화한다** — CH3 질문 1번의 실측 답
