**소요 90~120분.** 3주차 도전과제 3(chunked prefill)의 이월분을 해소하면서, **CH7의 PD 분리를 GPU 1장에서 다루는 대역**으로 씁니다.

---

## ⚠️ 이 편은 PD 분리 실습이 아닙니다

**진짜 PD 분리는 프리필 인스턴스와 디코드 인스턴스를 물리적으로 나누는 것**이라 GPU 2장 이상이 필요합니다. 이 환경에서는 못 합니다.

그런데 PD 분리가 **왜 하고 싶어지는가**는 GPU 1장에서 잴 수 있습니다. 동기가 되는 문제 — **프리필과 디코드가 같은 GPU에서 서로를 민다** — 는 여기서도 그대로 일어나니까요.

| | 프리필 | 디코드 |
|---|---|---|
| 성질 | **compute-bound** (긴 입력을 병렬 연산) | **memory-bound** (KV를 읽으며 한 토큰씩) |
| 한 번에 | 오래 걸린다 | 짧다 |
| 섞이면 | 디코드를 **멈춰 세운다** | — |

chunked prefill은 긴 프리필을 잘게 썰어 디코드 사이사이에 끼워 넣습니다. **간섭을 완화하지 제거하지 못합니다.** 제거하려면 물리적으로 나눠야 하고, 그게 PD 분리입니다.

**이 편이 재는 것은 "완화가 얼마나 되는가"이고, 남는 잔여 간섭이 "그래서 분리하고 싶어지는 이유"입니다.** 글에 이 구분을 명시하세요 — 3주차에 Triton으로 같은 처리를 했습니다.

---

## ⚠️ V0/V1 차이 — 축이 바뀐 이유

3주차 메모에 이렇게 적혀 있습니다:

> *ray-llm 2.44.1의 vLLM 0.7.2는 **V0 엔진**이고 `chunked_prefill_enabled=False`가 기본이라 **ON/OFF 비교가 가능한 환경**이다.*

사실이지만 **쓰지 않습니다.** [00의 0-5 단일 이미지 원칙](./4%EC%A3%BC%EC%B0%A8-00%20%EC%8B%A4%EC%8A%B5%20%EC%A4%80%EB%B9%84%EC%99%80%20%EC%B8%A1%EC%A0%95%20%EA%B7%9C%EC%B9%99.md) 때문입니다 — 이 편만 0.7.2에서 돌면 [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)·[03](./4%EC%A3%BC%EC%B0%A8-03%20%ED%94%84%EB%A6%AC%ED%94%BD%EC%8A%A4%20%EC%BA%90%EC%8B%B1%EC%9D%B4%20%EC%A7%80%EC%9A%B0%EB%8A%94%20%EC%97%B0%EC%82%B0.md)과 같은 표에 못 넣습니다. 3주차에 엔진 버전이 섞여 계층 비용을 7%p 과대계상할 뻔한 게 정확히 이 실수입니다.

**V1에서는 축을 바꿉니다.**

| | V0 (0.7.2) | **V1 (0.23.0) — 이번 주** |
|---|---|---|
| chunked prefill | 기본 OFF, 켤 수 있음 | **항상 켜짐** |
| 축 | `enable_chunked_prefill` ON/OFF | **`--max-num-batched-tokens` 크기** |
| 해석 | 있다/없다 | **얼마나 잘게 써느냐** |

청크를 `max_model_len`(4096) 이상으로 키우면 사실상 통짜 프리필이 되므로, **크기 축이 ON/OFF 축을 포함합니다.** 오히려 V0보다 나은 실험입니다 — 이분법 대신 곡선이 나오니까요.

> [00의 0-4](./4%EC%A3%BC%EC%B0%A8-00%20%EC%8B%A4%EC%8A%B5%20%EC%A4%80%EB%B9%84%EC%99%80%20%EC%B8%A1%EC%A0%95%20%EA%B7%9C%EC%B9%99.md)에서 `--max-num-batched-tokens`의 **하한**을 확인하세요. `--max-model-len`보다 작으면 거부하는 버전대가 있습니다.

---

## 가설

1. **청크를 작게 하면 디코드의 ITL 지터가 줄고, 프리필의 TTFT는 늘어난다.** 이 교환비가 이 편의 결과다.
2. **부하에 한 종류만 있으면 청크 크기를 바꿔도 아무 일도 안 일어난다.** 간섭이 없으므로. 이게 "조건부 이득"의 이 편 버전이다.
3. **아무리 잘게 썰어도 지터가 0이 되지는 않는다.** 남는 잔여분이 PD 분리의 존재 이유다.

## E2-1. 혼합 부하 만들기 ★ 이게 진짜 장벽입니다

`benchmark.py`는 시나리오를 **순차로** 돕니다(`run_scenario`가 시나리오마다 별도 `ThreadPoolExecutor`). `--scenarios prefill,decode`로 주면 프리필을 다 끝내고 디코드를 시작하므로 **둘이 안 섞입니다.**

**코드 수정 없이 섞는 법 — 두 프로세스를 동시에 띄웁니다.**

```bash
cd labs/wsl2-vllm-baseline
CHUNK=2048

# 디코드 쪽(피해자)을 먼저 띄워 정상 상태를 만든 뒤
python3 benchmark.py --scenarios decode --concurrency 8 \
  --requests-per-level 64 --output "results/e2-chunk${CHUNK}-decode.json" &
DECODE_PID=$!

sleep 10        # 디코드가 자리를 잡을 시간

# 프리필 쪽(가해자)을 그 위에 얹는다
python3 benchmark.py --scenarios prefill --concurrency 4 \
  --requests-per-level 32 --output "results/e2-chunk${CHUNK}-prefill.json"

wait $DECODE_PID
```

**대조군도 반드시 재세요** — 프리필 없이 디코드만 돌린 값이 있어야 "얼마나 밀렸는지"를 말할 수 있습니다.

```bash
python3 benchmark.py --scenarios decode --concurrency 8 \
  --requests-per-level 64 --output "results/e2-chunk${CHUNK}-decode-alone.json"
```

> ⚠️ **`sleep 10`을 빼지 마세요.** 두 프로세스가 동시에 시작하면 디코드가 정상 상태에 닿기 전에 프리필이 들어와 "밀렸다"의 기준선이 사라집니다.

> ⚠️ **처리량·goodput은 프로세스별로 읽으세요.** 두 JSON을 합산하면 안 됩니다 — 서로 다른 부하입니다. 보는 것은 **디코드 쪽의 ITL이 대조군 대비 얼마나 나빠졌나** 하나입니다.

**여유가 있으면 `[auto]` 작업**: `benchmark.py`에 `--mix prefill:4,decode:8` 형태의 옵션을 추가하면 위 셸 조합이 필요 없어지고 타임라인도 한 파일에 남습니다. 순수 로직이라 오프라인 테스트가 됩니다. **다만 두 프로세스 방식으로도 결론은 나오므로 필수는 아닙니다.**

## E2-2. 스윕

```bash
for CHUNK in 512 2048 8192; do
  docker rm -f vllm && sleep 5 && nvidia-smi

  docker run -d --name vllm --gpus all -p 8000:8000 \
    -v ~/.cache/huggingface:/root/.cache/huggingface \
    vllm/vllm-openai:v0.23.0 \
    --model Qwen/Qwen2.5-1.5B-Instruct --served-model-name qwen2.5-1.5b \
    --max-model-len 4096 --gpu-memory-utilization 0.85 --max-num-seqs 64 \
    --max-num-batched-tokens $CHUNK

  # 뜰 때까지 → 기동 로그 → 대조군 → 혼합 부하
done
```

`8192`는 `max_model_len`(4096)의 두 배라 **사실상 통짜 프리필**입니다 — V0의 "OFF"에 해당하는 자리입니다.

## 관측 — 채울 표

### ① 청크 크기 축

| 청크 | 디코드 ITL p50 (단독) | 디코드 ITL p50 (프리필과 혼합) | **열화율** | 디코드 ITL p95 (혼합) | 프리필 TTFT p50 |
|---|---|---|---|---|---|
| 512 | | | | | |
| 2048 | | | | | |
| 8192 (≒통짜) | | | | | |

**열화율 = (혼합 ITL − 단독 ITL) / 단독 ITL.** 이 열이 이 편의 결론입니다.

### ② 교환비 — 무엇을 사고 무엇을 파는가

| 청크 | 디코드가 얻는 것 | 프리필이 잃는 것 |
|---|---|---|
| 512 → 8192 | ITL 열화율 ___ → ___ | TTFT ___ → ___ |

### ③ 가설 2 확인 — 한 종류만 있을 때

| 청크 | 디코드만 (혼합 없음) 처리량 | 차이 |
|---|---|---|
| 512 | | 기준 |
| 8192 | | |

> **③에서 차이가 없어야 정상입니다.** 간섭이 없으면 청크 크기는 아무 일도 안 합니다. 이게 "조건부 이득"의 이 편 버전이고, ①과 나란히 놓아야 의미가 섭니다.

---

## 판단 기준

- ✅ **가설 1** — 청크가 작을수록 디코드 열화율이 낮고 프리필 TTFT가 높으면 교환비 확인. **양쪽이 같은 방향으로 움직이면** 통제 변수를 의심하세요(부하가 실제로 겹쳤는지).
- ✅ **가설 2** — ③에서 차이가 없으면 확인. **차이가 난다면** 청크 크기가 간섭 외의 것(예: 디코드 배치 구성)에도 영향을 준다는 뜻이니, 그것 자체가 기록거리입니다.
- ✅ **가설 3** — 512에서도 열화율이 0이 아니면 확인. **그 잔여분이 PD 분리의 존재 이유**이고, 글의 결론 문장이 여기서 나옵니다: *"청크는 간섭을 잘게 나눌 뿐 없애지 못한다. 없애려면 GPU를 나눠야 한다."*
- ⚠️ **열화율이 10% 안에서만 움직이면** 부하가 충분히 안 겹친 것입니다. 프리필 쪽 동시성을 올리거나 `requests-per-level`을 늘려 보세요. 그래도 안 되면 **"12GB·1.5B에서는 간섭이 관측 한계 아래였다"** 고 쓰고 넘어가세요 — 못 본 것을 봤다고 쓰는 것보다 낫습니다.
