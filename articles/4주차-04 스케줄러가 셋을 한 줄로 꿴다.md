## 왜 이 편이 있는가 — 3주차 글과의 차별점

3주차 글은 **"재 봤더니 이렇더라"** 로 끝났습니다. 계층 셋의 가격표를 만들었고, *"요청 경로에 서 있는가"* 라는 기준까지 세웠지만, 그 기준은 **관측에서 귀납한 것**이었습니다.

이번엔 다릅니다. [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)·[02](./4%EC%A3%BC%EC%B0%A8-02%20%ED%94%84%EB%A6%AC%ED%95%84%EC%9D%B4%20%EB%94%94%EC%BD%94%EB%93%9C%EB%A5%BC%20%EB%AF%B8%EB%8A%94%20%EA%B0%92.md)·[03](./4%EC%A3%BC%EC%B0%A8-03%20%ED%94%84%EB%A6%AC%ED%94%BD%EC%8A%A4%20%EC%BA%90%EC%8B%B1%EC%9D%B4%20%EC%A7%80%EC%9A%B0%EB%8A%94%20%EC%97%B0%EC%82%B0.md)이 각각 다른 이야기처럼 보이지만 **코드에서는 같은 함수의 같은 변수를 건드립니다.** 그걸 소스로 짚으면 글이 *"왜 그런가"* 까지 답합니다.

교재 CH8이 정확히 이 질문을 던집니다 (`study/Ch8.md:9`):

> *vLLM이 요청 단위가 아니라 **토큰 단위로 스케줄링**한다는 것은 구체적으로 무엇이 다르며, `num_computed_tokens`와 `num_tokens_with_spec`의 차이를 좁히는 것이 왜 청크드 프리필·프리픽스 캐싱 같은 **모든 최적화의 공통 메커니즘**이 되는가?*

**이 편은 이 질문 하나에 답하는 것이 목표입니다.** 그리고 공식 도전과제이기도 합니다 (`Ch8.md:496` — *"vLLM 주요 동작의 소스 코드 분석 해보기"*).

## E4-1. 소스 꺼내기 — 컨테이너 안에 이미 있습니다

클론할 필요 없습니다. 실습에 쓴 이미지 안에 설치된 그 코드를 읽는 게 **버전이 정확히 맞아 더 낫습니다.**

```bash
# 컨테이너가 떠 있다면 그대로, 아니면 임시로 하나
docker run --rm -it --entrypoint bash vllm/vllm-openai:v0.23.0

python -c "import vllm, os; print(os.path.dirname(vllm.__file__)); print(vllm.__version__)"
```

호스트로 꺼내 두면 편집기로 읽기 좋습니다:

```bash
CID=$(docker create vllm/vllm-openai:v0.23.0)
docker cp "$CID:/usr/local/lib/python3.12/site-packages/vllm/v1" ./vllm-v1-src
docker rm "$CID"
```

> ⚠️ **파이썬 버전 경로는 이미지마다 다릅니다.** 위 `python -c`로 실제 경로를 먼저 확인하세요. 3주차의 *"번들 런타임이 `python`을 부르는데 이미지엔 `python3`만 있었다"* 와 같은 종류의 함정입니다.

| 무엇 | 어디쯤 |

## E4-2. 답을 찾을 질문 넷

읽으면서 아래 표를 채웁니다. **파일명과 줄 번호를 반드시 적으세요** — 글의 근거가 됩니다.

### ① 토큰 예산은 어디서 정해지고 어떻게 소모되나

한 스케줄 스텝에서 처리할 토큰 총량이 있고, 요청들이 그걸 나눠 갖습니다. 그 예산의 출처가 `--max-num-batched-tokens`입니다.

| 찾을 것 | 파일:줄 | 메모 |
|---|---|---|
| 예산 변수의 이름 | | |
| 예산이 `--max-num-batched-tokens`에서 오는 경로 | | |
| 요청 하나가 예산을 깎는 지점 | | |

### ② 세 최적화가 각각 어느 항을 건드리나 ★ 이 표가 이 편의 결론

| 최적화 | 무엇을 바꾸나 (한 줄) | 파일:줄 |
|---|---|---|
| **chunked prefill** ([02](./4%EC%A3%BC%EC%B0%A8-02%20%ED%94%84%EB%A6%AC%ED%95%84%EC%9D%B4%20%EB%94%94%EC%BD%94%EB%93%9C%EB%A5%BC%20%EB%AF%B8%EB%8A%94%20%EA%B0%92.md)) | 프리필 요청이 한 스텝에 가져갈 토큰 수의 **상한** | |
| **prefix caching** ([03](./4%EC%A3%BC%EC%B0%A8-03%20%ED%94%84%EB%A6%AC%ED%94%BD%EC%8A%A4%20%EC%BA%90%EC%8B%B1%EC%9D%B4%20%EC%A7%80%EC%9A%B0%EB%8A%94%20%EC%97%B0%EC%82%B0.md)) | 시작 시점의 `num_computed_tokens`를 **0이 아닌 값으로** 올려 줌 | |
| **추측 디코딩** ([01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)) | 목표치를 `num_tokens_with_spec`으로 **늘려** 한 스텝에 여러 토큰을 밀어 봄 | |

**셋 다 "지금 어디까지 계산됐나(`num_computed_tokens`)"와 "어디까지 가야 하나" 사이의 거리를 조작합니다.** 캐싱은 출발점을 앞으로 당기고, 청크는 한 걸음의 보폭을 제한하고, 추측 디코딩은 한 걸음을 여러 칸으로 늘립니다. **그래서 셋이 한 줄로 꿰입니다.**

### ③ 관심사 분리 — CH8의 첫 질문 (`Ch8.md:5`)

> *왜 Scheduler는 "모델을 모른 채" 최적화를 결정하고, GPUWorker는 "스케줄링을 모른 채" 연산만 하는가?*

| 찾을 것 | 파일:줄 | 메모 |
|---|---|---|
| Scheduler가 모델 아키텍처를 참조하는 곳이 **정말 없는가** | | 있다면 그게 반례 |
| Scheduler → Executor로 넘어가는 자료구조 | | 이 경계가 분리의 실체 |

**답은 "미래 대비성"** 입니다 — 새 모델·새 하드웨어가 나와도 상위 계층을 재설계하지 않고 해당 계층만 교체하면 됩니다. **코드에서 그 경계를 짚으면 이게 수사가 아니라 구조라는 게 보입니다.**

### ④ 측정과 대조 — 숫자가 코드와 맞는가

| 관측 | 코드에서 예상되는 것 | 맞았나 |
|---|---|---|
| [02](./4%EC%A3%BC%EC%B0%A8-02%20%ED%94%84%EB%A6%AC%ED%95%84%EC%9D%B4%20%EB%94%94%EC%BD%94%EB%93%9C%EB%A5%BC%20%EB%AF%B8%EB%8A%94%20%EA%B0%92.md)에서 청크를 줄이면 디코드 ITL 지터가 준다 | 프리필이 예산을 덜 가져가므로 디코드 몫이 남는다 | |
| [03](./4%EC%A3%BC%EC%B0%A8-03%20%ED%94%84%EB%A6%AC%ED%94%BD%EC%8A%A4%20%EC%BA%90%EC%8B%B1%EC%9D%B4%20%EC%A7%80%EC%9A%B0%EB%8A%94%20%EC%97%B0%EC%82%B0.md)에서 공유가 없으면 이득이 0 | 블록 조회가 다 빗나가 `num_computed_tokens`가 안 올라간다 | |
| [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)에서 고동시성이면 손해 | spec 토큰도 **같은 예산**을 먹으므로 다른 요청 자리를 뺏는다 | |

> ★ **세 번째 줄이 이 시리즈 전체의 결론입니다.** 추측 디코딩이 고동시성에서 손해인 이유가 "GPU가 바빠서"라는 막연한 설명이 아니라 **"같은 토큰 예산을 두고 경쟁하기 때문"** 이라는 구체적 기전으로 바뀝니다. 측정([01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md))과 코드(이 편)가 만나는 자리입니다.

## E4-3. 프레임워크 평가 축 — CH8의 세 번째 질문

`Ch8.md:11`이 묻습니다: *"어떤 프레임워크가 최고인가"가 아니라 "내 SLO·워크로드·운영 현실에 어떤 프레임워크가 맞는가"를 물어야 한다면, 구체적으로 어떤 축이…*

이번 주에 vLLM 하나만 실측했으므로 **비교는 못 합니다.** 대신 **이 시리즈가 만든 조건표를 평가 축으로 되돌려 쓸 수 있습니다.**

| 축 | 이 시리즈가 준 근거 |
|---|---|
| 내 워크로드에 **프리픽스 공유**가 있나 | [03](./4%EC%A3%BC%EC%B0%A8-03%20%ED%94%84%EB%A6%AC%ED%94%BD%EC%8A%A4%20%EC%BA%90%EC%8B%B1%EC%9D%B4%20%EC%A7%80%EC%9A%B0%EB%8A%94%20%EC%97%B0%EC%82%B0.md)의 2×2 — 있으면 SGLang의 RadixAttention도 후보에 든다 |
| **프리필/디코드 비중**이 어떤가 | [02](./4%EC%A3%BC%EC%B0%A8-02%20%ED%94%84%EB%A6%AC%ED%95%84%EC%9D%B4%20%EB%94%94%EC%BD%94%EB%93%9C%EB%A5%BC%20%EB%AF%B8%EB%8A%94%20%EA%B0%92.md)의 열화율 — 크면 PD 분리를 지원하는 스택이 필요 |
| **동시성 수준**이 어디쯤인가 | [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)의 뒤집히는 지점 — 낮으면 추측 디코딩 지원이 선택 기준이 된다 |

> **"3~6개월마다 재평가하라"는 결론은 "정답이 없다"가 아니라 "정답이 계속 바뀐다"는 뜻입니다.** 그리고 이 시리즈의 주장과 같은 모양입니다 — **조건이 바뀌면 답이 바뀝니다.** 글의 결론에서 이 두 줄을 겹치면 CH7과 CH8이 한 문장으로 닫힙니다.
