## 0. 준비

### 0-1. ⚠️ 디스크 먼저 — 이번 주 첫 번째 명령

3주차에 Triton vLLM 이미지(36.3GB)를 받다가 C: 잔여 공간이 0.1GB가 됐고, ext4.vhdx가 더 못 늘어나 `libacl.so.1: Input/output error`와 함께 **k3s까지 죽었습니다.**

```bash
df -h /                      # WSL 내부
docker system df             # 이미지가 먹은 양
```

Windows 쪽 C: 드라이브 여유도 함께 보세요. 이번 주에 새로 받는 건 draft 모델 **~1GB**뿐이지만, **3주차 잔해가 남아 있으면 그것부터 정리**해야 합니다.

```bash
docker images                                  # 뭐가 남았는지 먼저 눈으로
docker rmi nvcr.io/nvidia/tritonserver:24.12-py3   # 27.4GB — 이번 주엔 안 씁니다
docker rmi rayproject/ray-llm:2.44.1-py311-cu124   # 11.9GB — 〃
```

> **지우기 전에 3주차 결과가 전부 `results/`에 있는지 확인하세요.** 측정 원본은 이미지가 아니라 JSON에 있으므로 이미지는 지워도 됩니다. 다시 필요해지면 다시 받으면 되지만, **결과 JSON은 다시 못 만듭니다.**

**켜졌는지 확인하는 법 — 두 곳을 교차로 봅니다.**

```bash
docker logs vllm 2>&1 | grep -iE "speculat|ngram|draft"   # ① 기동 로그
curl -s localhost:8000/metrics | grep spec_decode           # ② 메트릭 존재 여부
```

**둘 다 비어 있으면 안 켜진 것입니다.** 측정을 시작하지 마세요.

### 0-6. 공통 기동 명령 — 여기서만 옵션이 갈립니다

```bash
docker run -d --name vllm --gpus all -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:v0.23.0 \
  --model Qwen/Qwen2.5-1.5B-Instruct \
  --served-model-name qwen2.5-1.5b \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 64 \
  <<< 여기에 각 편의 옵션 >>>
```

**앞 네 줄은 2주차 B1 기준선과 같은 값입니다.** `--max-num-seqs`만 16 → 64로 올렸습니다(3주차에서 64가 처리량 최적으로 확인됨).

> 모델은 이미 `~/.cache/huggingface`에 있습니다 — **다시 안 받습니다.**

### 0-9. 반복 규칙 ★ 이번 주에 특히 걸립니다

3주차에서 확인했습니다 — **c≤32는 재현 오차 1.3% 안, c=64는 10%까지 흔들립니다.**

[01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)이 c=64를 씁니다. 그래서:

- **c=64 구간은 팔마다 2회씩** 재고 둘 다 기록하세요
- **10% 안의 차이는 "차이 없음"으로 씁니다.** 추측 디코딩의 손해가 8%로 나오면 그건 손해가 아니라 잡음입니다
- c=1·4는 1회로 충분합니다 — 여기가 이득이 가장 크게 나올 구간이라 오히려 안전합니다

> 반복을 못 한 것 자체는 흠이 아닙니다. **안 했는데 한 것처럼 쓰는 것**이 문제입니다.

| **팔마다 KV 예산을 기록하고 비교 가능 여부를 먼저 판정** | draft 팔은 KV가 줄어든다. 판정 없이 빼면 두 원인이 섞인다 |
| **워크로드를 조건으로 다루기** | 이번 주는 동시성만 축이 아니다. **부하의 성질**(반복이 있나·프리픽스를 공유하나)이 두 번째 축 |
| **10% 안은 차이가 아니다** | 0-9 |
| **손해도 결과로 기록** | 추측 디코딩이 느려지는 건 실패가 아니라 **이 글의 결론** |
| **`vllm:*` 카운터는 반드시 차분** | 기동 이후 누적. 팔을 바꿀 때마다 컨테이너가 새로 뜨므로 이번 주는 비교적 안전하지만, 같은 팔에서 여러 부하를 돌리면 섞인다 |

| 증상 | 원인 | 대응 |

| **E1** `--speculative-config`에서 기동 실패 | JSON 스키마 불일치 | `docker logs vllm`에 검증 오류가 남는다. 0-4의 `--help` 출력과 대조 |

| **E1** 수용률이 0에 수렴 | ngram이 맞힐 게 없는 워크로드 | **정상 동작입니다.** ngram은 출력이 입력을 되풀이할 때만 맞는다 — [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)의 워크로드 축 참조. **이 관측 자체가 결과** |
| **E1** draft 팔이 OOM | 12GB에 1.5B+0.5B+KV가 안 맞음 | `--gpu-memory-utilization`을 낮추지 **말고** 먼저 KV 예산 로그를 확인. 낮추면 vanilla와 조건이 더 벌어진다. 안 되면 draft 팔을 포기하고 ngram만 (잘라내기 1순위) |
| **E1** vanilla보다 느린데 수용률은 높음 | **정상 — 이게 결론** | 배치가 이미 GPU를 채우면 검증 연산이 순수 낭비다. 동시성 축과 함께 표로 |
| **E2** 청크 크기를 바꿔도 아무 변화 없음 | 부하에 프리필·디코드가 안 섞임 | 두 프로세스 동시 실행 확인 ([02](./4%EC%A3%BC%EC%B0%A8-02%20%ED%94%84%EB%A6%AC%ED%95%84%EC%9D%B4%20%EB%94%94%EC%BD%94%EB%93%9C%EB%A5%BC%20%EB%AF%B8%EB%8A%94%20%EA%B0%92.md)). 한 종류만 있으면 간섭이 없어서 당연히 안 변한다 |
| **E2** `--max-num-batched-tokens`가 거부됨 | 하한 미만 | `--max-model-len`보다 작으면 거부하는 버전대가 있다. 0-4에서 하한 확인 |
| **E3** 캐시를 켰는데 적중률 0 | 요청이 프리픽스를 안 나눔 | `--unique-prefix`가 켜져 있는지 확인. 이 옵션이 **일부러 적중을 막습니다** |
