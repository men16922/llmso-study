## 0. 준비

### 0-1. 디스크 — 확인은 하되, 이번 주의 진짜 경계는 다른 곳입니다

3주차에 Triton vLLM 이미지(36.3GB)를 받다가 C: 잔여 공간이 0.1GB가 됐고, ext4.vhdx가 더 못 늘어나 `libacl.so.1: Input/output error`와 함께 **k3s까지 죽었습니다.** 그래서 이 절이 맨 앞에 있었습니다.

```bash
df -h /                      # WSL 내부
```

**2026-08-27 실측으로는 여유가 충분합니다** — WSL `/`에 780G, Windows C:에 198GB. 3주차 잔해(docker에 Triton 27.4GB + 36.3GB)는 **containerd가 아니라 docker에 있어 이번 주 실험과 무관**하므로 굳이 지울 이유도 없습니다.

> ★ **그래서 이번 주의 경계는 디스크가 아니라 이겁니다 — `docker`에 새 이미지를 받지 마세요.** 실험은 전부 k3s containerd에 이미 있는 이미지로 돕니다. `docker run vllm/...`을 치는 순간 같은 이미지를 **한 벌 더** 받게 되고, 그건 디스크 문제이기 이전에 **B1 기준선과 다른 실행 경로**를 만드는 통제 변수 문제입니다.

### 0-2. WSL 세션 붙잡기 ★ 여전히 필수 (방법은 바뀌었습니다)

WSL은 **distro 안에 살아 있는 세션이 없으면** VM을 내립니다. 그러면 k3s 파드가 `Completed`/`Unknown`이 되어 측정이 끊깁니다.

```powershell
# 독립 Windows 프로세스로 띄운다 — 창을 지킬 필요가 없다
Start-Process wsl.exe -ArgumentList '-d','Ubuntu','-u','root','--','sleep','infinity' `
  -WindowStyle Hidden -PassThru
```

살아 있는지 확인: `Get-Process wsl`. **재부팅하면 다시 띄우세요.**

> ❌ **`.wslconfig`의 `vmIdleTimeout=-1`은 안 먹습니다** (WSL 2.7.8.0에서 확인). `[wsl2]`·`[experimental]` 양쪽에 넣고 BOM까지 제거해 재적용했지만 100초 뒤 그대로 내려갔습니다. **원인이 유휴 타이머가 아니라 "세션이 없으면 내린다"** 이기 때문이고, systemd로 k3s가 `active`여도 마찬가지입니다.
>
> ⚠️ 여전히 **에이전트가 띄운 백그라운드 태스크는 이 환경에서 강제 종료됩니다.** 위 `Start-Process`는 그 관리 밖의 독립 프로세스라 살아남습니다. **긴 측정 자체는 포그라운드로** 돌리세요.

### 0-3. GPU 배타성 ★ 이번 주는 단순합니다

**GPU 1장·8000 포트 1개**뿐인 건 그대로지만, 이번 주는 **전부 같은 컨테이너를 다시 띄우는 것**이라 계층 간 전환이 없습니다.

```bash
# 매니페스트가 strategy: Recreate라 옛 파드가 먼저 죽고 새 파드가 뜬다.
# GPU 1장에서 RollingUpdate는 교착하므로 이 전략을 바꾸지 말 것.
source labs/wsl2-vllm-baseline/redeploy.sh
nvidia-smi                        # ★ VRAM이 실제로 반환됐는지 눈으로 확인
```

> ★ **VRAM 반환 확인은 이번 주에 특히 중요합니다.** [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)이 팔 세 개를 번갈아 띄우는데, 반환 전에 다음을 띄우면 **KV 예산이 조용히 절반이 되어** 팔 사이 비교가 통째로 깨집니다. 3주차 미해결 관측(`Maximum concurrency` 59.50x vs 28.77x)이 이 가설과 맞습니다.

### 0-6. 공통 기동 명령 — 여기서만 옵션이 갈립니다

2주차 B1을 만든 그 배포를 그대로 다시 씁니다. 실험별 플래그는 **`EXTRA_ARGS` env 한 곳**으로 들어갑니다(2026-08-27 매니페스트에 신설).

```bash
cd labs/wsl2-vllm-baseline
source redeploy.sh

# 공통 기준선 — 앞 세 값은 2주차 B1과 같고, max-num-seqs만 16 → 64
redeploy MAX_MODEL_LEN=4096 GPU_MEMORY_UTILIZATION=0.85 MAX_NUM_SEQS=64 \
         EXTRA_ARGS='<<< 여기에 각 편의 옵션 >>>'
```

`redeploy`가 ① env 설정 ② 롤아웃 대기와 **실패 감지** ③ 포트포워딩 재기동 ④ `/v1/models`가 실제로 응답할 때까지 폴링을 해 줍니다. ④를 `sleep 5`로 때우면 파드가 준비되기 전에 벤치마크가 시작돼 **조용히 쓰레기 데이터**가 나옵니다.

> ⚠️ **`EXTRA_ARGS` 값에 JSON을 넣을 때 공백을 쓰지 마세요.** 매니페스트에서 `$EXTRA_ARGS`는 **따옴표 없이** 전개돼 셸 단어 분리로 여러 플래그가 됩니다(그래야 `--max-num-batched-tokens 512`가 인자 둘이 됩니다). 그래서 0-4의 평탄화 `--spec-*` 플래그를 쓰는 게 안전합니다. 이 규칙은 `test_manifest.py`가 감시합니다.

> 모델은 이미 PVC(`huggingface-cache`)에 있습니다 — **다시 안 받습니다.**

### 0-7. 기동 로그 캡처 ★ 3주차 규칙 유지

```bash
# 매 기동 직후 — 파일명에 팔 이름을 넣을 것
ARM="e1-ngram"
kubectl -n llm-serving-lab logs deploy/vllm-baseline \
  | grep -iE "kv cache|gpu blocks|maximum concurrency|speculat|ngram|draft|chunked|prefix" \
  | tee "results/${ARM}-startup.txt"
```

찾는 줄:

```
GPU KV cache size: N tokens
Maximum concurrency for 4096 tokens per request: 59.50x
```

> **이 두 줄이 팔 사이 비교가 성립하는지를 판정합니다.** [01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)의 draft 팔은 KV 예산이 **반드시 줄어듭니다**(draft 모델이 VRAM을 먹으므로). 얼마나 줄었는지를 모르면 "추측 디코딩 때문에 느려졌다"와 "KV가 좁아져서 느려졌다"를 구별할 수 없습니다.

### 0-9. 반복 규칙 ★ 이번 주에 특히 걸립니다

3주차에서 확인했습니다 — **c≤32는 재현 오차 1.3% 안, c=64는 10%까지 흔들립니다.**

[01](./4%EC%A3%BC%EC%B0%A8-01%20%EC%B6%94%EC%B8%A1%20%EB%94%94%EC%BD%94%EB%94%A9%EC%9D%80%20%EC%96%B8%EC%A0%9C%20%EC%86%90%ED%95%B4%EA%B0%80%20%EB%90%98%EB%8A%94%EA%B0%80.md)이 c=64를 씁니다. 그래서:

- **c=64 구간은 팔마다 2회씩** 재고 둘 다 기록하세요
- **10% 안의 차이는 "차이 없음"으로 씁니다.** 추측 디코딩의 손해가 8%로 나오면 그건 손해가 아니라 잡음입니다
- c=1·4는 1회로 충분합니다 — 여기가 이득이 가장 크게 나올 구간이라 오히려 안전합니다

> 반복을 못 한 것 자체는 흠이 아닙니다. **안 했는데 한 것처럼 쓰는 것**이 문제입니다.
