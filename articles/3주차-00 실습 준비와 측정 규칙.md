## 0. 준비

### 0-1. WSL 세션 붙잡기 ★ 2주차와 동일, 여전히 필수

WSL이 유휴 상태에서 systemd에 poweroff를 요청해 k3s가 내려갑니다.

```powershell
# Windows PowerShell — 실습 내내 이 창을 닫지 않는다
wsl -d Ubuntu -u root -- sleep infinity
```

> ⚠️ **이 머신에서는 백그라운드 태스크가 반복 강제 종료됩니다.** 이 keeper는 **사람이 별도 창에서** 띄우세요. 에이전트가 백그라운드로 띄우면 죽습니다 — 2주차에 이것 때문에 측정이 한 번 끊겼습니다.

### 0-2. GPU 배타성 ★ 이번 주 가장 중요한 준비

**GPU 1장·8000 포트 1개**뿐이라 세 실험이 서로 배타적입니다. 앞의 것을 안 내리면 다음이 OOM 또는 `Pending`으로 뜨지 않습니다.

| 실험 | GPU를 쓰는 것 | 시작 전 반드시 내릴 것 |
|---|---|---|
| [01](./3%EC%A3%BC%EC%B0%A8-01%20Ray%20Serve%EB%9D%BC%EB%8A%94%20%EA%B3%84%EC%B8%B5%EC%9D%98%20%EA%B0%80%EA%B2%A9.md) C3 | RayService 워커 파드 | `vllm-baseline` (2주차 기준선) |
| [02](./3%EC%A3%BC%EC%B0%A8-02%20KV%20cache%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%20%EB%8F%99%EC%8B%9C%EC%84%B1%20%EC%83%81%ED%95%9C.md) B3 | **01의 RayService를 그대로 재사용** | (없음 — 01에서 이어짐) |
| [03](./3%EC%A3%BC%EC%B0%A8-03%20Triton%20dynamic%20batching.md) C2 | Triton 컨테이너 | **RayService 전체** + `vllm-baseline` |

```bash
# 01 시작 전
kubectl -n llm-serving-lab scale deploy/vllm-baseline --replicas=0

# 03 시작 전 — 01·02를 완전히 끝낸 뒤
kubectl delete -f labs/rayserve-on-k8s/rayservice-qwen.yaml
kubectl -n llm-serving-lab get pod          # 전부 사라질 때까지 확인
nvidia-smi                                   # VRAM이 실제로 반환됐는지 ★
```

> ★ **`nvidia-smi`로 VRAM 반환을 눈으로 확인하세요.** 2주차의 미해결 관측(`Maximum concurrency` 59.50x vs 28.77x)이 **직전 파드의 VRAM 반환 지연** 가설과 맞습니다. 반환 전에 다음을 띄우면 KV 예산이 조용히 절반이 됩니다.

### 0-3. 이미지 풀 ★ 시간이 오래 걸리므로 가장 먼저

**별도 창에서 사람이 직접 띄우세요.**

```bash
# 01 C3용 — KubeRay operator + ray-llm (~10GB)
helm repo add kuberay https://ray-project.github.io/kuberay-helm/ && helm repo update

# 03 C2용 — Triton
docker pull nvcr.io/nvidia/tritonserver:24.12-py3
docker images | grep tritonserver
```

> ⚠️ **Triton 이미지 크기가 문서마다 다릅니다.** 노션 CH3 실습 기록은 **9.63GB**(디스크 사용 27.4GB)인데, 이 저장소의 기존 계획에는 `~17GB`로 적혀 있습니다. **실제 값을 확인해 기록**하고 문서를 정정하세요. 디스크 여유가 부족하면 `docker system prune -a`.

### 0-4. 메트릭 이름 ★ 이번 주에 쓰는 것이 2주차에 빗나갔던 그 이름입니다

2주차 실측에서 1순위 이름 6개 중 2개가 빗나갔는데, **그중 하나가 바로 이번 주에 쓸 KV cache 메트릭**입니다.

| 쓰는 곳 | 1순위 이름 | v0.23.0 실측 |
|---|---|---|
| **[02](./3%EC%A3%BC%EC%B0%A8-02%20KV%20cache%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%20%EB%8F%99%EC%8B%9C%EC%84%B1%20%EC%83%81%ED%95%9C.md) KV cache 사용률** | `vllm:gpu_cache_usage_perc` | ❌ **없음** → **`vllm:kv_cache_usage_perc`가 정답** |
| 01 큐·실행 요청 수 | `vllm:num_requests_running` / `_waiting` | ✅ 그대로 |
| 01 TTFT | `vllm:time_to_first_token_seconds_bucket` | ✅ 그대로 |
| (chunked prefill) prefix cache | `vllm:prefix_cache_queries_total` / `_hits_total` | ✅ 그대로 (`gpu_` 접두 버전은 **없음**) |

```bash
curl -s localhost:8000/metrics | grep -oE '^vllm:[a-z0-9_]+' | sort -u
```

> ⚠️ **문자 클래스에 `0-9`를 반드시 넣으세요.** `[a-z_]+`로 뽑으면 `vllm:e2e_...`가 **`vllm:e`로 둔갑**합니다. 2주차에 이 오타로 잘못된 결론을 냈다가 되잡았습니다.

**Ray Serve로 띄운 vLLM도 같은 메트릭을 내는지 확인하세요.** 다르면 그 자체가 기록거리입니다 — 01의 계층 오버헤드 절에 넣을 소재입니다. 목록은 `results/metrics-rayserve.txt`로 남기세요.

### 0-5. 기동 로그 캡처 ★ 이번 주 신설 규칙, 가장 중요

**2주차의 뼈아픈 누락입니다.** `Maximum concurrency` 값을 관측하고도 메모로만 남겨서 증빙이 없습니다. 재현하려면 롤아웃마다 5~15분이 듭니다.

**롤아웃할 때마다 반드시 파일로 저장하세요.**

```bash
# 매 롤아웃 직후 — 파일명에 설정값을 넣을 것
CFG="len4096-seqs64-util085"
kubectl -n llm-serving-lab logs deploy/vllm-baseline 2>/dev/null \
  | grep -iE "kv cache|gpu blocks|maximum concurrency|max_num_seqs|max_model_len" \
  | tee "results/b3-startup-${CFG}.txt"
```

RayService인 경우 파드 이름이 다릅니다:

```bash
POD=$(kubectl -n llm-serving-lab get pod -l ray.io/node-type=worker -o name | head -1)
kubectl -n llm-serving-lab logs "$POD" \
  | grep -iE "kv cache|gpu blocks|maximum concurrency" \
  | tee "results/b3-startup-${CFG}.txt"
```

찾는 줄은 이 형태입니다:

```
GPU KV cache size: N tokens
Maximum concurrency for 4096 tokens per request: 59.50x
```

> **이 한 줄이 [02](./3%EC%A3%BC%EC%B0%A8-02%20KV%20cache%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%20%EB%8F%99%EC%8B%9C%EC%84%B1%20%EC%83%81%ED%95%9C.md) 전체의 정답지입니다.** 손계산을 먼저 적어두고 이 값과 대조하는 것이 실험의 값어치입니다.

### 0-6. 환경 기록 ★ 스터디 공통 규칙

2주차 [0-6](./2%EC%A3%BC%EC%B0%A8-00%20%EC%8B%A4%EC%8A%B5%20%EC%A4%80%EB%B9%84%EC%99%80%20%EC%B8%A1%EC%A0%95%20%EA%B7%9C%EC%B9%99.md)의 스크립트를 그대로 씁니다. **3주차에 추가로 기록할 것**:

# Ray Serve 쪽 vLLM 버전 확인 ★ 반드시
POD=$(kubectl -n llm-serving-lab get pod -l ray.io/node-type=worker -o name | head -1)
kubectl -n llm-serving-lab exec "$POD" -- python -c "import vllm; print(vllm.__version__)"

### 0-7. 반복 규칙

2주차와 동일합니다 — 스터디 규칙은 최소 3회 반복 후 대표값이지만 시간상 타협합니다.

- **핵심 구간만 3회**: 01의 계층 오버헤드 동시성 8·16(붕괴점 주변)
- 나머지는 1회 측정하되 **글에 "1회 측정"이라고 명시**
- `--requests-per-level`을 100 이상으로 키워 백분위를 안정시킴

> 반복을 못 한 것 자체는 흠이 아닙니다. **안 했는데 한 것처럼 쓰는 것**이 문제입니다.

### 0-8. 스모크 테스트

각 실험을 시작하기 전에 엔드포인트가 실제로 응답하는지 확인합니다.

```bash
cd labs/wsl2-vllm-baseline
python3 benchmark.py --concurrency 1,4 --requests-per-level 2 --output results/smoke-week3.json
```

## 측정 규칙 — 3주차에 특히 지킬 것

| 규칙 | 이유 |
|---|---|
| **통제 변수를 먼저 고정하고 그다음에 스윕** | 01의 계층 오버헤드를 B1과 같은 조건으로 먼저 끝낸 **뒤에** 02의 `engine_kwargs`를 건드릴 것. 순서를 바꾸면 01이 무의미해짐 |
| **손계산을 로그보다 먼저 적기** | 로그가 정답을 알려주므로, 보고 나서 계산하면 검증이 아니라 사후 맞추기가 됨 |
| **카운터는 반드시 차분** | Triton 메트릭은 기동 이후 누적. 그냥 나누면 이전 실험이 섞임 |
| **실패도 결과로 기록** | `slots=64` 기동 실패는 실패가 아니라 KV 예산의 관측 결과 |
| **롤아웃마다 기동 로그 저장** | 0-5 참조 |

## 트러블슈팅 (3주차)

2주차 [트러블슈팅 표](./2%EC%A3%BC%EC%B0%A8-00%20%EC%8B%A4%EC%8A%B5%20%EC%A4%80%EB%B9%84%EC%99%80%20%EC%B8%A1%EC%A0%95%20%EA%B7%9C%EC%B9%99.md)가 여전히 유효합니다. 이번 주에 새로 만날 것:

| 증상 | 원인 | 대응 |
|---|---|---|
| **C3** 워커 파드가 `Pending` | GPU를 `vllm-baseline`이 점유 | `scale deploy/vllm-baseline --replicas=0` |
| **C3** 워커가 GPU를 못 봄 | `runtimeClassName: nvidia` 누락 | 제공 매니페스트에는 있음 — 공식 예제를 그대로 쓴 건 아닌지 확인 |
| **C3** 헤드가 GPU를 잡아 워커가 못 뜸 | `num-gpus`가 헤드에도 잡힘 | 매니페스트는 헤드를 `"0"`으로 둠 |
| **C3** OOM / 파드 Evicted | WSL2 23Gi에 head+worker가 안 맞음 | `requests` 합이 20Gi 이하인지 (`test_worker_memory_fits_wsl2_allocation`) |
| **C3** RayService가 계속 `Initializing` | 모델 다운로드 중 | `kubectl logs`로 진행 확인. B1의 PVC 캐시를 마운트하면 빨라짐 |
| **C3** 오버헤드가 음수 (Ray Serve가 더 빠름) | 통제 변수 위반 | **vLLM 버전을 양쪽 다 기록**(0-6). 같은 버전이 아니면 비교가 아님 |
| **B3** `serveConfigV2` 변경이 반영 안 됨 | 롤아웃이 아직 진행 중 | `kubectl describe rayservice`로 전환 상태 확인. 새 RayCluster가 뜬 뒤 전환됨 |
| **B3** `make check` 실패 | `rayservice-qwen.yaml`을 직접 고침 | `ManifestTest`가 네 값을 지킴. **스윕은 별도 파일로** |
| **B3** 손계산과 로그가 2배 이상 어긋남 | MHA 공식을 GQA 모델에 적용 | `config.json`의 `num_key_value_heads`를 쓸 것 ([02](./3%EC%A3%BC%EC%B0%A8-02%20KV%20cache%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%20%EB%8F%99%EC%8B%9C%EC%84%B1%20%EC%83%81%ED%95%9C.md) 참조) |
| **B3** 같은 설정인데 `Maximum concurrency`가 절반 | 직전 파드 VRAM 미반환(유력, 미확인) | 0-2의 `nvidia-smi` 확인. **이것 자체가 관측 결과이므로 기록** |
| **C2** 모델 `load`가 400/500 | `dims`에 배치 차원을 넣었거나 ONNX 배치 축이 고정 | `dims`에서 배치 차원 제거, `dynamic_axes`로 재-export. `docker logs triton` |
| **C2** 평균 배치 크기가 계속 1.00 | config 미반영 | `curl localhost:8009/v2/models/mobilenet_v2/config`로 실제 값 확인 → 안 되면 `docker restart triton` |
| **C2** `docker: permission denied` | WSL2에서 docker 그룹 미등록 | `sudo usermod -aG docker $USER` 후 셸 재시작 |
| **C2** `--gpus all`에서 기동 실패 | WSL2 nvidia-container-toolkit 미설정 | `--gpus`를 빼고 CPU로 진행 — 절대값은 낮아지지만 **delay 축의 경향은 그대로** |
