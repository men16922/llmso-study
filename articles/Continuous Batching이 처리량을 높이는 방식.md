## 이 글의 배경

앞선 실습 [WSL2를 로컬 GPU Kubernetes 개발 환경으로 사용하기](./WSL2%EB%A5%BC%20%EB%A1%9C%EC%BB%AC%20GPU%20Kubernetes%20%EA%B0%9C%EB%B0%9C%20%ED%99%98%EA%B2%BD%EC%9C%BC%EB%A1%9C%20%EC%82%AC%EC%9A%A9%ED%95%98%EA%B8%B0.md)에서는 Windows의 GPU를 WSL2 → Docker → K3s 파드까지 연결하고, DCGM Exporter와 Prometheus·Grafana로 GPU 상태를 볼 수 있게 만들었다. 거기서 확인한 것은 **GPU가 보이는가**까지였다.

이 글은 그 환경 위에 vLLM을 올려 **그 GPU가 실제로 얼마나 일하는가**를 잰 기록이다. 새로 만든 인프라는 없다. 앞의 실습에서 세운 k3s·Prometheus 위에 매니페스트 하나를 올렸고, 이 글의 증빙 캡처도 그때 구성한 모니터링에서 나왔다.

한 가지 더 있다. 앞선 실습에서 **WSL2는 `DCGM_FI_PROF_*` 계열 프로파일링 메트릭을 노출하지 않는다**는 것을 확인했다(Grafana 대시보드의 Tensor Core 패널이 비어 있었다). 이 제약이 이번 측정 방법을 정했다. GPU 사용률은 `max-num-seqs`가 1이든 64든 부하만 걸리면 똑같이 100%를 찍기 때문에, **GPU 계층 지표로는 배칭 효과를 잴 수 없다.** 그래서 이 글은 한 층 위인 **서빙 엔진(vLLM)이 노출하는 지표**와 클라이언트 측정값으로 답을 찾는다.

| 층 | 지표 | 배칭을 잴 수 있나 |
|---|---|---|
| GPU (DCGM) | `DCGM_FI_DEV_GPU_UTIL` | ❌ 어떤 설정이든 부하 시 100% |
| GPU (DCGM) | `DCGM_FI_PROF_*` | ❌ WSL2에서 미노출 |
| 서빙 엔진 (vLLM) | `num_requests_running` / `_waiting` | ✅ 처리 중·대기 중 요청 수가 그대로 보인다 |
| 클라이언트 | TTFT · ITL · SLO 충족률 | ✅ 사용자가 겪는 값 |

## 0. 먼저 알아둘 용어

본문에 반복해서 나오는 말만 미리 정리한다.

| 용어 | 쉽게 말하면 |
|---|---|
| **토큰(token)** | 모델이 한 번에 만들어 내는 글자 조각. 한글은 보통 1~2글자가 한 토큰 |
| **prefill / decode** | prefill은 입력을 한꺼번에 읽는 단계, decode는 토큰을 하나씩 만드는 단계 |
| **배칭(batching)** | 여러 요청의 다음 토큰을 한 번에 계산하는 것 |
| **sequence** | 모델이 생성 중인 문장 하나. 이번 실험에서는 요청 하나 = sequence 하나 |
| **iteration** | 스케줄러가 배치를 한 번 구성해 토큰을 한 스텝 만드는 주기 |
| **TTFT** | 요청을 보낸 뒤 **첫 토큰**이 돌아올 때까지 걸린 시간 |
| **ITL** | 첫 토큰 이후 **토큰 하나당** 걸린 시간. 교재의 TPOT와 같은 값 |
| **처리량(throughput)** | 서버 전체가 초당 만들어 낸 토큰 수 |
| **SLO 충족률** | 정한 지연 시간 기준(여기서는 TTFT ≤ 0.5s)을 지킨 요청의 비율 |
| **KV Cache** | 이미 계산한 토큰의 중간 결과를 담아 두는 GPU 메모리 영역 |

## 1. Continuous Batching이 필요한 이유

LLM은 문장 전체를 한 번에 만들지 않는다. **토큰을 하나씩** 만든다.

토큰 하나를 만들 때마다 GPU는 모델 가중치를 읽어야 한다. 이때 요청이 하나뿐이면 GPU는 그 하나를 위해 가중치를 전부 읽는다. 요청이 64개라면, 가중치를 한 번 읽은 김에 64개의 다음 토큰을 함께 계산할 수 있다. 특히 decode 단계는 작은 배치에서 메모리 대역폭의 영향을 크게 받기 때문에, 여러 요청을 함께 처리할수록 GPU 활용률과 전체 토큰 처리량이 높아진다.

> **쉽게 말하면**: 배칭은 GPU를 빠르게 만드는 기술이 아니다. 어차피 치러야 하는 메모리 읽기 비용을 여러 요청이 나눠 내게 하는 방식이다.

문제는 **요청마다 출력 길이가 다르다**는 점이다.

| 방식 | 동작 | 문제 |
|---|---|---|
| **Static Batching** | 처음 만든 배치를 끝까지 유지 | 짧은 요청이 끝나도 긴 요청이 끝날 때까지 그 자리를 재사용하기 어렵다 |
| **Continuous Batching** | 완료된 요청을 iteration 단위로 빼고 새 요청을 넣음 | 빈 자리를 곧바로 재사용할 수 있다 |

Continuous Batching의 핵심은 **배치를 요청 전체가 끝날 때까지 고정하지 않는 것**이다.

```
Iteration 1: A B C
Iteration 2: A B C
Iteration 3: A B C  ← A 완료
Iteration 4: D B C  ← 다음 요청 D 투입
```

이런 방식을 **iteration-level scheduling**이라고 부른다.

## 2. max-num-seqs는 무엇을 정하는가

vLLM에서 `--max-num-seqs`는 **한 scheduler iteration에서 처리할 수 있는 최대 sequence 수**다.

이번 실험처럼 `1 request → 1 sequence` 구조에서는 **동시에 처리할 수 있는 폭**, 즉 자리 수처럼 생각하면 이해하기 쉽다. 이 글에서도 편의상 `slots=16`처럼 표기한다.

다만 실제 처리 가능한 요청 수가 이 값 하나로 정해지지는 않는다. 아래 네 가지가 함께 작용한다.

| 요소 | 역할 |
|---|---|
| `max-num-seqs` | iteration당 최대 sequence 수 |
| `max-num-batched-tokens` | iteration당 처리할 수 있는 최대 토큰 수 |
| KV Cache | 동시에 유지할 수 있는 context의 메모리 한계 |
| prompt / output 길이 | 요청 하나가 쓰는 연산량과 KV Cache 크기 |

따라서 `max-num-seqs=64`로 설정했다고 해서 항상 64개 요청이 같은 방식으로 처리된다는 뜻은 아니다. 이 구분은 [6절](#6-maximum-concurrency-로그는-어떻게-읽어야-하나)에서 다시 다룬다.

## 3. 실험 구성

비교 변수는 `max-num-seqs` 하나이고 나머지는 모두 고정했다.

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 4080 **Laptop** GPU, 12,282 MiB |
| Driver | 581.57 |
| OS / 커널 | WSL2, `6.18.33.1-microsoft-standard-WSL2` |
| 서빙 엔진 | `vllm/vllm-openai:v0.23.0` (컨테이너 이미지 고정) |
| 모델 | `Qwen/Qwen2.5-1.5B-Instruct`, dtype auto |
| `max-model-len` | 4096 |
| `gpu-memory-utilization` | 0.85 |
| tensor parallel | 1 (GPU 1장) |
| 오케스트레이션 | k3s on WSL2, `strategy: Recreate` |
| **비교 변수** | `max-num-seqs` = **1 / 16 / 64** |
| **부하 축** | 동시성 1 / 2 / 4 / 8 / 16 / 32 / 64 |
| 시나리오 | `short`(입출력 ~50토큰), `decode`(긴 출력) |
| 레벨당 요청 수 | `short` 100건, `decode` 30건, 큐 관측 200건 |
| 측정일 | 2026-08-15 |

슬롯 값을 바꿀 때마다 파드를 새로 띄우므로, 실제로 반영됐는지 매번 파드 로그에서 확인했다.

```
non-default args: {..., 'max_model_len': 4096, 'gpu_memory_utilization': 0.85, 'max_num_seqs': 64}
```

### 보는 지표

- **Output Throughput** — 서버가 초당 생성한 토큰 수
- **TTFT p95** — 요청의 95%가 첫 토큰을 받기까지 걸린 시간의 경계
- **ITL p50** — 첫 토큰 이후 토큰 하나당 간격의 중앙값
- **SLO 충족률** — 개별 요청 중 `TTFT ≤ 0.5s`를 만족한 비율
- **running / waiting** — vLLM 내부에서 실행 중이거나 대기 중인 요청 수

> 여기서 **SLO 충족률**은 vLLM이 정의하는 `request_goodput(req/s)`과 다르다. 이 글에서는 사용자가 허용한 TTFT 안에 응답을 시작한 요청의 **비율**을 보기 위해 따로 계산했다.

Prefix Cache가 결과를 실제보다 좋게 만들지 않도록 각 요청의 prefix는 다르게 구성했다(`--unique-prefix`). 이 장치를 빼면 두 번째 요청부터 prefill이 캐시로 해결되어 TTFT가 실제보다 짧게 나온다.

> **측정 반복 횟수**: 스터디 공통 규칙은 최소 3회 반복 후 대표값이다. 이번 측정은 **각 지점 1회**다. 대신 레벨당 요청 수를 100건으로 늘려 백분위를 안정시켰다. 반복 측정은 다음 편으로 미룬다.

## 4. 결과

### 4-1. max-num-seqs를 늘리면 처리량이 증가한다

**처리량 (tok/s), `short` 시나리오**

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| 1 | 111.0 | 108.8 | 112.1 |
| 2 | 113.5 | 213.9 | 215.3 |
| 4 | 113.4 | 413.7 | 420.9 |
| 8 | 112.8 | 780.2 | 769.0 |
| 16 | 113.1 | **1333.1** | 1354.3 |
| 32 | 113.0 | 1391.0 | 2053.0 |
| 64 | 112.6 | 1340.0 | **2626.7** |

![max-num-seqs에 따른 처리량 변화 — slots=1은 거의 일정하고, slots=16은 동시성 16 이후 증가가 멈추며, slots=64는 64까지 계속 증가한다](./figures/fig-b1-throughput.svg)

세 설정의 양상이 다르다.

- **`slots=1`** — 동시성을 1에서 64로 64배 높여도 처리량은 111 → 113 tok/s로 거의 변하지 않았다. 한 번에 한 요청만 처리하므로 동시 요청이 늘어도 줄만 길어진다.
- **`slots=16`** — 동시성 16까지는 거의 선형으로 증가한다(108.8 → 1333.1, 12.3배). 16을 넘으면 1391 → 1340 tok/s로 증가가 멈춘다.
- **`slots=64`** — 동시성 64까지 계속 증가한다. 증가가 멈추는 지점이 `max-num-seqs` 값을 따라 이동한다.

그림에서 `slots=16`(주황)과 `slots=64`(초록)은 동시성 16까지 겹쳐 있다. 두 선이 갈라지는 지점이 `slots=16`의 처리 한도다.

GPU와 모델, 부하는 모두 동일하고 `max-num-seqs` 값만 달랐다. 그 결과 처리량은 **113 tok/s에서 2,627 tok/s로 약 23배** 차이가 났다.

> **주의**: GPU가 23배 빨라진 것이 아니다. 여러 요청을 한 iteration에서 함께 처리해 GPU를 더 효율적으로 쓴 결과다.

### 4-2. 처리 한도를 넘으면 요청은 큐에서 기다린다

처리량이 멈추는 지점에서 TTFT가 어떻게 변하는지 함께 보면 원인이 드러난다.

**TTFT p95 (s), `short` 시나리오**

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| 1 | 0.027 | 0.036 | 0.022 |
| 2 | 0.581 | 0.040 | 0.035 |
| 4 | 1.694 | 0.041 | 0.037 |
| 8 | 3.623 | 0.061 | 0.060 |
| 16 | 7.411 | 0.105 | 0.101 |
| 32 | 14.985 | **0.745** | 0.198 |
| 64 | 28.374 | **1.826** | 0.306 |

![동시성에 따른 TTFT p95 변화 — 로그 눈금. slots=1은 동시성에 비례해 증가하고, slots=16은 동시성 32에서 SLO 기준선을 넘는다](./figures/fig-b1-ttft.svg)

`slots=1`에서 동시성을 2배씩 올릴 때마다 TTFT도 2배씩 오른다(0.58 → 1.69 → 3.62 → 7.41 → 14.99 → 28.37). 처리량은 그대로인데 대기 시간만 늘었다. 늘어난 동시성이 **전부 대기 시간으로 바뀐 것**이다.

`slots=16`에서도 동시성 16을 넘으면 같은 일이 일어난다. c=16에서 0.105초였던 TTFT가 c=32에서 0.745초로 7배 증가한다. 4-1에서 처리량 증가가 멈춘 바로 그 지점이다.

**SLO 충족률 (%)** — `TTFT ≤ 0.5s`를 만족한 요청 비율

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| 1 | 100.0 | 100.0 | 100.0 |
| 2 | **41.0** | 100.0 | 100.0 |
| 4 | 5.0 | 100.0 | 100.0 |
| 8 | 2.0 | 100.0 | 100.0 |
| 16 | 2.0 | 100.0 | 100.0 |
| 32 | 2.0 | **48.0** | 100.0 |
| 64 | 2.0 | **23.0** | 100.0 |

전 구간에서 HTTP 성공률은 100/100이다. 실패한 요청은 하나도 없다. 그런데 `slots=16`의 동시성 64에서 **SLO 안에 응답을 시작한 요청은 23%뿐**이다. 성공률만 모니터링했다면 이 구간을 정상으로 판단했을 것이다.

#### 서버 내부에서는 무슨 일이 일어났나

`max-num-seqs=16`으로 고정하고 동시성 4 → 16 → 64로 각각 200개 요청을 6분간 보낸 뒤, 같은 구간의 vLLM 내부 지표를 Prometheus에서 조회했다.

| 동시성 | running | waiting | 처리량 | TTFT p95 |
|---|---|---|---|---|
| 16 | 16 | 0 | 1,598.3 tok/s | 0.107s |
| 64 | **16** | **48** | 1,602.8 tok/s | 14.840s |

![처리 중(running)과 대기 중(waiting) 요청 수 — running은 16에서 더 증가하지 않고, 동시성 64가 되는 순간 waiting이 0에서 48로 증가한다](./figures/fig-b2-queue.svg)

```
16 requests → running 16 / waiting  0
64 requests → running 16 / waiting 48
```

동시성을 16 → 64로 **4배** 늘렸지만 처리량은 1,598 → 1,603 tok/s로 0.3% 증가에 그쳤다. `running`은 16에서 더 올라가지 않고, 초과한 48개 요청이 전부 `waiting`으로 갔다. **64 − 16 = 48**이 정확히 맞는다.

> **쉽게 말하면**: 처리 한도를 넘긴 요청은 추가 처리량으로 바뀌지 않는다. 큐에 쌓이고, 그만큼 TTFT가 길어진다.

### 4-3. ITL은 거의 변하지 않는다

TTFT가 급증하는 동안 **토큰 간격은 거의 그대로**였다.

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| 1 | 0.0088 | 0.0090 | 0.0088 |
| 16 | 0.0088 | 0.0102 | 0.0102 |
| 32 | 0.0088 | 0.0103 | 0.0120 |
| 64 | 0.0088 | 0.0105 | **0.0156** |

<details>
<summary>동시성 전 구간 ITL p50 (s)</summary>

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| 1 | 0.0088 | 0.0090 | 0.0088 |
| 2 | 0.0087 | 0.0090 | 0.0090 |
| 4 | 0.0087 | 0.0092 | 0.0091 |
| 8 | 0.0088 | 0.0094 | 0.0093 |
| 16 | 0.0088 | 0.0102 | 0.0102 |
| 32 | 0.0088 | 0.0103 | 0.0120 |
| 64 | 0.0088 | 0.0105 | 0.0156 |

</details>

`slots=16`의 동시성 16 → 64 구간에서 TTFT는 14배 증가했지만 ITL은 0.0102 → 0.0105로 3% 증가하는 데 그쳤다. 처리량이 23배가 되는 `slots=64`의 동시성 64에서도 ITL은 0.0088 → 0.0156으로 1.8배다.

이유는 1절의 구조에 있다. 배치에 자리를 잡은 요청은 매 iteration마다 토큰을 하나씩 받는다. 배치가 커져도 iteration 시간 자체는 크게 늘지 않는다. 반면 자리를 못 잡은 요청은 **첫 토큰조차 받지 못한다.**

> **사용자 입장에서 번역하면**: 부하가 올라갈 때 나타나는 증상은 "글자가 느리게 나온다"가 아니라 "**응답이 시작되지 않는다**"에 가깝다. ITL 0.0156s는 사용자당 초당 64토큰으로 읽는 속도보다 빠르다. 부하를 감지하려면 ITL이 아니라 TTFT를 봐야 한다.

### 4-4. 출력이 길수록 차이가 커진다

긴 출력을 만드는 `decode` 시나리오에서는 차이가 더 크다.

| 설정 | 동시성 | 처리량 | TTFT p95 | SLO 충족률 |
|---|---|---|---|---|
| `slots=1` | 32 | 115.1 tok/s | **130.660s** | 3.1% |
| `slots=16` | 32 | 1,643.9 tok/s | 5.044s | 50.0% |
| `slots=64` | 32 | **2,851.9 tok/s** | **0.191s** | 100% |

<details>
<summary>decode 시나리오 전체 표</summary>

| 동시성 | slots=1 | slots=16 | slots=64 |
|---|---|---|---|
| **처리량 (tok/s)** | | | |
| 1 | 114.7 | 115.3 | 115.8 |
| 8 | 115.2 | 822.3 | 820.9 |
| 32 | 115.1 | 1643.9 | **2851.9** |
| **TTFT p95 (s)** | | | |
| 1 | 0.034 | 0.031 | 0.023 |
| 8 | **31.159** | 0.072 | 0.075 |
| 32 | **130.660** | 5.044 | **0.191** |
| **SLO 충족률 (%)** | | | |
| 8 | 3.3 | 100.0 | 100.0 |
| 32 | 3.1 | 50.0 | **100.0** |

`slots=1`에서 동시 요청 32개를 보내면 마지막 요청은 첫 글자를 보는 데 **2분 이상** 기다린다. 같은 지점에서 `slots=64`는 0.191초다. TTFT는 684배, 처리량은 24.8배 차이가 난다.

출력이 길면 요청 하나가 자리를 더 오래 쓴다. 그래서 동시에 처리할 수 있는 sequence 수가 적을수록 뒤의 요청이 오래 기다린다. **출력 길이가 요청마다 다른 LLM에서 Continuous Batching이 특히 중요한 이유**가 여기에 있다.

ITL은 여기서도 변화 폭이 작다. `slots=64` 동시성 32에서 0.0111s로, `slots=1`의 0.0088s 대비 26% 증가했다.

### 4-5. 처리량과 지연 시간의 교환 관계

앞의 표들은 같은 데이터를 다른 각도에서 본 것이다. 처리량과 TTFT p95를 한 평면에 놓으면 어떤 설정을 골라야 하는지가 한눈에 보인다. (★ = 파레토 최적)

| 구성 | 동시성 | 처리량 (tok/s) | TTFT p95 (s) | SLO 충족률 | SLO | 파레토 |
|---|---|---|---|---|---|---|
| slots=64 | 64 | **2626.7** | 0.306 | 100.0 | ✅ | ★ |
| slots=64 | 32 | 2053.0 | 0.198 | 100.0 | ✅ | ★ |
| slots=16 | 32 | 1391.0 | 0.745 | 48.0 | ❌ | |
| slots=64 | 16 | 1354.3 | 0.101 | 100.0 | ✅ | ★ |
| slots=16 | 64 | 1340.0 | 1.826 | 23.0 | ❌ | |
| slots=16 | 16 | 1333.1 | 0.105 | 100.0 | ✅ | |
| slots=64 | 8 | 769.0 | 0.060 | 100.0 | ✅ | ★ |
| slots=64 | 1 | 112.1 | 0.022 | 100.0 | ✅ | ★ |
| slots=1 | 64 | 112.6 | 28.374 | 2.0 | ❌ | |

> **SLO를 지키면서 낼 수 있는 최대 처리량: 2,626.7 tok/s** (slots=64, 동시성 64, TTFT p95 0.306s)

여기서 읽을 수 있는 것이 두 가지다.

- **파레토 경계는 모두 `slots=64`다.** 같은 동시성에서 `slots=16`은 처리량이 비슷하면서 TTFT가 더 크거나 같다. 이 워크로드에서는 `slots=16`을 선택할 이유가 없다.
- **최저 TTFT와 최고 처리량이 같은 설정에서 나왔다.** 둘 다 `slots=64`이고 차이는 동시성뿐이다. 즉 이 실험에서 처리량과 지연 시간을 맞바꾸는 노브는 `max-num-seqs`가 아니라 **얼마나 많은 요청을 동시에 보내느냐**였다.

<details>
<summary>지연 공식과 실측값 비교 — 큐 대기 시간은 어디에 잡히나</summary>

교재 CH4는 다음 공식을 제시한다.

```
E2E latency = TTFT + ITL × (N − 1)
```

교재는 실제 E2E에 "요청 대기, 네트워크 지연, 라우팅 시간, 확장 오버헤드"가 더해진다고도 설명한다. 즉 이 공식은 모델 실행 시간만 설명하므로, 남는 차이가 모델 밖에서 쓰인 시간이 된다.

| 구성 | 동시성 | N(토큰) | TTFT (s) | ITL (s) | 공식 예측 | 실측 E2E | 잔차 |
|---|---|---|---|---|---|---|---|
| slots=1 | 1 | 50.1 | 0.024 | 0.0088 | 0.455 | 0.553 | +0.098 |
| slots=1 | 4 | 46.9 | 1.268 | 0.0087 | 1.669 | 1.653 | −0.016 |
| slots=1 | 64 | 48.7 | 21.989 | 0.0088 | 22.408 | 22.460 | +0.052 |
| slots=16 | 16 | 45.5 | 0.046 | 0.0102 | 0.501 | 0.601 | +0.100 |
| slots=16 | 64 | 49.9 | 1.421 | 0.0105 | 1.934 | 1.861 | −0.073 |
| slots=64 | 64 | 45.4 | 0.164 | 0.0156 | 0.859 | 0.907 | +0.047 |

실험 전에는 "동시성이 오를수록 잔차가 커지고, 그것이 큐 대기의 클라이언트 측 증거"라고 예상했다. 그런데 잔차는 동시성과 무관하게 **+0.05~0.10초 근처**에 머문다. `slots=1`의 동시성 64는 28초를 기다렸는데도 잔차는 +0.052초다.

큐 대기 시간이 이미 TTFT에 포함되어 있기 때문이다. 클라이언트가 재는 TTFT는 요청을 보낸 시점부터 첫 토큰을 받을 때까지의 시간이고, 큐에서 기다린 시간도 그 안에 들어간다. 따라서 잔차에는 큐 대기가 남지 않는다.

남은 잔차는 **고정 오버헤드**로 보인다. HTTP 왕복, `kubectl port-forward` 경유, 토큰화가 여기에 해당한다. 동시성과 무관하게 절대값이 일정한 점이 근거다.

부호가 음수로 뒤집히는 구간(`slots=16` 동시성 64 등)은 공식의 한계를 보여준다. 이 구간은 요청들이 큐에서 오래 기다렸다가 한꺼번에 배치에 들어가므로 토큰 간격 분포가 한쪽으로 치우친다. p50 ITL을 곱한 값이 실제 총합보다 커진다. 이 공식을 쓸 때는 p50이 아니라 **평균 ITL**을 사용해야 한다.

</details>

## 5. 결과 해석

### 5-1. GPU 사용률 100%가 처리량 한계를 뜻하지는 않는다

1주차 Cloud Run 실습에서 동시 요청이 늘자 SLO 충족률이 절반 아래로 떨어지는 지점이 있었다. 그때는 "GPU가 포화했다"로 넘겼다.

하지만 GPU 사용률은 그 전에 이미 100%에 가까웠는데도 처리량은 한동안 계속 증가했다. GPU 사용률 100%는 **GPU가 일하고 있다**는 뜻이지 **더 처리할 수 없다**는 뜻이 아니다. 배치를 더 효율적으로 구성하면 같은 GPU에서 처리량을 더 높일 수 있다.

따라서 GPU utilization 하나만 보고 서버가 최대 성능에 도달했다고 판단하면 안 된다.

### 5-2. 포화 이후에는 처리량보다 TTFT가 먼저 나빠진다

서버가 처리할 수 있는 범위 안에서는 동시성을 늘릴수록 처리량이 증가했다. 한계를 넘은 뒤에는 다음 순서로 진행된다.

```
요청 증가
→ running 한도 도달
→ waiting 증가
→ 처리량 증가 정체
→ TTFT 증가
→ SLO 충족률 감소
```

이 과정에서 HTTP 응답은 전부 성공(200)이다. 성공률 기반 알람은 울리지 않는다. 그런데 사용자는 이미 느린 서비스를 겪고 있다.

`slots=16`의 동시성 32는 처리량 기준으로는 가장 높은 지점(1,391 tok/s)이지만 SLO 충족률은 48%다. 처리량만 보고 설정을 정하면 사용자 절반이 기준을 벗어난다.

### 5-3. max-num-seqs는 높을수록 무조건 좋은 값이 아니다

이번 워크로드에서는 64가 가장 좋은 결과를 냈다. 그러나 이 값을 모든 모델과 GPU에 그대로 적용할 수는 없다.

배치가 커지면 KV Cache 사용량과 iteration당 연산량도 함께 증가한다. 모델이 커지거나 요청의 context가 길어지면 같은 값에서도 결과가 달라진다. 실제 환경에서는 **처리량과 지연 시간을 함께 측정해 적절한 값을 찾아야 한다.**

## 6. Maximum concurrency 로그는 어떻게 읽어야 하나

vLLM을 시작하면 다음과 같은 로그가 나온다.

```
Maximum concurrency for 4,096 tokens per request: 59.50x
```

이 값은 "최대 59개 요청만 처리할 수 있다"는 hard limit가 **아니다.** 모든 요청이 `max-model-len=4096`만큼 KV Cache를 쓴다고 가정했을 때의 **추정 동시성**이다. 실제 요청이 더 짧으면 더 많은 sequence가 동시에 유지될 수 있다.

두 값을 구분해야 한다.

| 값 | 의미 |
|---|---|
| `max-num-seqs` | scheduler가 한 iteration에서 처리하도록 허용하는 sequence 수 |
| `Maximum concurrency ...` | KV Cache 용량을 `max-model-len` 기준으로 환산한 **참고값** |

실제 capacity는 요청 길이와 KV Cache 사용량까지 포함해 부하 테스트로 확인해야 한다.

<details>
<summary>이 값이 롤아웃마다 달라진 기록</summary>

이번 실습의 10번 롤아웃에서 이 로그를 모으면 다음과 같다.

| 설정 | 관측값 |
|---|---|
| `max-num-seqs=1` | 61.00x, 61.00x |
| `max-num-seqs=16` | **32.61x**, 60.37x, 60.37x, 60.37x |
| `max-num-seqs=64` | 59.50x, 59.50x, **28.77x** |

같은 설정인데 값이 2배 차이 나기도 했다. 굵게 표시한 두 이상치는 둘 다 **직전에 다른 파드가 GPU를 쓰던 롤아웃**이다(32.61x는 7B 모델 파드 직후, 28.77x는 중단된 실행의 파드 직후). `strategy: Recreate`가 이전 파드를 먼저 내리지만 VRAM 반환이 그보다 늦어, 새 파드가 남은 메모리로 KV Cache를 잡은 것으로 보인다. 다만 그 시점의 VRAM을 `nvidia-smi`로 측정하지는 않았으므로 인과 관계는 정황에 근거한 추정이다.

실무적으로는 롤아웃 직후 이 로그를 확인해 두는 편이 좋다. 값이 크게 줄어 있으면 그만큼 KV Cache 여유가 없다는 신호다.

</details>

## 7. 운영에서 확인할 지표

LLM Serving에서 성공률만 모니터링하는 것으로는 부족하다.

| 지표 | 무엇을 보는가 |
|---|---|
| **Output Throughput** | GPU가 실제로 얼마나 많은 토큰을 처리하는가 |
| **TTFT p95** | 사용자가 첫 응답을 얼마나 오래 기다리는가 |
| **SLO 충족률 / Goodput** | 성공 여부뿐 아니라 허용 지연 시간 안에 처리되는가 |
| **`vllm:num_requests_waiting`** | 현재 처리 능력을 넘어선 요청이 있는가 |

특히 `num_requests_waiting > 0`이 지속되면서 TTFT가 함께 증가한다면 **서버가 포화 구간에 들어갔다는 신호**로 볼 수 있다. 이번 측정에서는 이 값이 0에서 48로 오른 시점이 곧 SLO 충족률이 무너진 시점이었다.

<details>
<summary>이 실습에서 실제로 부딪힌 운영 이슈</summary>

- **`startupProbe`를 최대 20분까지 허용해야 했다.** 모델 로딩(가중치 다운로드 + CUDA 그래프 캡처)이 그만큼 걸린다. 기본값으로 두면 파드가 준비되기 전에 종료되어 재시작이 반복된다.
- **재배포 후 `/v1/models`를 폴링해 실제 응답을 확인해야 했다.** `rollout status`가 성공을 반환한 뒤에도 엔드포인트가 아직 응답하지 않는 구간이 있다. 고정된 `sleep`으로 대체하면 서버가 준비되기 전에 측정이 시작된다.
- **롤아웃 실패는 non-zero 종료 코드로 처리해야 했다.** 응답하지 않는 엔드포인트에 벤치마크를 실행하면 오류 대신 의미 없는 측정값이 기록된다.

</details>

## 8. 실험의 한계와 다음 단계

이번 결과는 방향을 확인하기에는 충분하지만 절대적인 capacity 수치로 사용하면 안 된다.

1. **각 지점을 1회 측정했다.** 작은 차이(예: `slots=16` 1333.1 vs `slots=64` 1354.3)는 노이즈일 수 있다. 이 글의 결론은 배 단위로 차이가 나는 항목에만 근거한다.
2. **모든 요청을 동시에 시작하는 wave 형태다.** 실제 서비스에 가까운 arrival-rate 기반 테스트가 필요하다.
3. **전력 상한(TGP)을 확인하지 못했다.** 랩탑 GPU라 `nvidia-smi`가 `power.limit`을 `[N/A]`로 보고한다. 절대값은 이 기기 고유값으로 봐야 하고, 비교는 설정 간 상대값으로만 유효하다.
4. **GPU 한 장, 1.5B 모델, 단일 레플리카다.** 라우팅·오토스케일·멀티 노드는 범위 밖이고, 더 큰 모델에서는 결과가 달라질 수 있다.

다음 실험에서 확인할 것.

1. `max-model-len`과 KV Cache가 실제 동시성에 미치는 영향
2. `vllm:request_queue_time_seconds`로 본 실제 큐 대기 시간 분포
3. Prefix Cache를 켰을 때 처리량과 TTFT 변화
4. request arrival rate를 올리며 capacity knee 확인
5. 네 가지 배칭 방식 비교 — 교재 CH3의 자작 서버로 static/continuous 구현(C1), Triton `dynamic_batching`(C2), Ray Serve 계층의 오버헤드(C3)

> **다음 편 예고 — 교재 코드에서 발견한 것.** 교재 CH3의 자작 서버(`ch03/single_model_llm_serving`)는 `main.py`의 `async def` 핸들러 안에서 동기 호출을 한다. uvicorn 이벤트 루프가 그 사이 막히므로 동시 요청이 사실상 순차 처리된다. 이 서버에서 "동시성을 올려도 처리량이 안 오른다"를 관측하면 원인은 배칭이 아니라 이벤트 루프다. 이번 편 `slots=1`과 증상은 같지만 원인이 다르다. 다음 편에서 `async def`를 `def`로 바꾼 전후를 비교해 둘을 분리한다.

## 정리

Continuous Batching의 핵심은 "배치 크기를 크게 만드는 것"이 아니다. **완료된 요청을 iteration마다 빼고, 빈 자리에 새 요청을 계속 넣어 GPU가 할 일을 유지하는 것**이다.

이번 실험에서 이 차이는 같은 GPU에서 약 **23배의 토큰 처리량 차이**로 나타났다. 그리고 더 중요한 결과가 하나 더 있다.

> **처리 한도를 넘긴 요청은 처리량을 높이지 않는다. 큐를 만들고 TTFT를 증가시킨다.**

따라서 LLM Serving의 capacity를 판단할 때는 GPU utilization이나 HTTP 성공률만 볼 것이 아니라 **처리량 + TTFT + 대기 큐 + SLO 충족률**을 함께 봐야 한다.

```bash
# 0. 배포 (슬롯 값은 env로 빠져 있다)
kubectl apply -f labs/wsl2-vllm-baseline/k8s/vllm-baseline.yaml

# 1. max-num-seqs를 바꿔가며 스윕
cd labs/wsl2-vllm-baseline

for SLOTS in 1 16 64; do
  redeploy MAX_NUM_SEQS=$SLOTS || continue   # 기동 실패는 건너뛴다
  confirm_slots                              # 실제 반영 확인
  python3 benchmark.py --scenarios short \
    --concurrency 1,2,4,8,16,32,64 --requests-per-level 100 \
    --unique-prefix --ttft-slo 0.5 --e2e-slo 10 \
    --output results/b1-slots-$SLOTS-short.json

  # 긴 출력(4-4)은 포인트를 줄여 따로 한 번 더
  python3 benchmark.py --scenarios decode \
    --concurrency 1,8,32 --requests-per-level 30 \
    --unique-prefix --ttft-slo 0.5 --e2e-slo 30 \
    --output results/b1-slots-$SLOTS-decode.json
done

# 2. 표는 손으로 만들지 않는다
python3 summarize_results.py results/b1-slots-*-short.json \
  --label-regex 'slots-(\d+)' --label-format 'slots={}' --all
python3 summarize_results.py results/b1-slots-*-short.json \
  --label-regex 'slots-(\d+)' --label-format 'slots={}' --pareto --ttft-slo 0.5

# 3. 큐가 보이는 구간. max-num-seqs를 16으로 두고 길게 건다
redeploy MAX_NUM_SEQS=16
python3 benchmark.py --scenarios decode \
  --concurrency 4,16,64 --requests-per-level 200 \
  --unique-prefix --ttft-slo 0.5 --e2e-slo 30 \
  --output results/b2-queue.json

# 4. 그래프 — 위 JSON에서 SVG를 직접 만든다 (외부 의존성 없음)
python3 tools/make_figures.py        # → articles/figures/*.svg
```
