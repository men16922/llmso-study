## 0. 1주차와 무엇이 달라지는가

한 문장으로 정리하면 이렇습니다.

> **1주차**는 *요청 하나 안에서 무슨 일이 일어나는가*(prefill/decode, KV cache, 병목)였고,
> **2주차**는 *요청 여럿을 어떻게 받아낼 것인가*(배칭, 동시성, 스케일링, 측정)입니다.

1주차 노트 끝에 남겨둔 질문 — **"배칭이 decode의 memory bound를 완화한다면 배치를 무한정 키우면 왜 안 되나?"** — 의 답이 오늘 범위 한복판에 있습니다. 그 질문을 들고 들어가면 CH3의 절반은 이미 따라간 셈입니다.

## 1. 배칭 세 가지 ★ 오늘 가장 중요

서빙 서버는 대부분 배칭으로 한 번에 여러 요청을 처리합니다. 방식은 셋입니다. (p.188)

| 방식 | 동작 | 문제 |
|---|---|---|
| **Static batching** | 배치가 **가득 찰 때까지 기다렸다가** 추론 시작 | 먼저 온 요청이 오래 기다림 |
| **Dynamic batching** | 배치가 차거나 **설정한 시간이 지나면** 시작 | 대기 상한은 생기지만 여전히 요청 단위 |
| **Continuous batching** | 추론을 **계속 돌리면서**, 슬롯이 비는 대로 새 요청을 밀어 넣음 | — |

> vLLM·SGLang·TensorRT-LLM 같은 추론 엔진은 견고한 continuous batching을 구현하며, **요청이 토큰 단위로 배칭**됩니다. static batching 대비 지연을 최소화합니다. (p.189)

TensorRT-LLM은 같은 것을 **in-flight batching**이라고 부릅니다 — 강의나 문서에서 두 용어가 섞여 나오면 같은 것으로 읽으세요. (p.112)

### 그래서 1주차 질문의 답 ★★

> **배치 크기는 지연과 처리량을 맞바꿉니다.** 배치를 키우면 전체 처리량은 올라가지만 **개별 사용자의 지연은 나빠집니다.** 모델·인스턴스·지연 목표·예산에 맞는 지점을 찾으려면 **여러 배치 크기에 걸쳐 성능을 시험**해야 합니다. (p.190)

무한정 키우면 안 되는 이유는 "어떤 임계값을 넘으면 터져서"가 아니라 **애초에 트레이드오프이기 때문**입니다. 처리량을 사는 대가로 사용자 지연을 파는 것이고, 어디까지 팔지는 SLA가 정합니다.

## 2. 동시성 — 배칭과 오토스케일링이 만나는 지점

배칭 설정이 왜 인프라 문제가 되는지가 여기서 드러납니다.

> 트래픽 기반 오토스케일링을 제대로 운영하려면 **인스턴스 하나가 동시 트래픽을 얼마나 감당하는지**를 정확히 알아야 합니다. (p.188)

- 오토스케일링 설정의 **concurrency target**과 레플리카의 **batch size는 서로 맞아야** 합니다. (p.190)
- 활성 레플리카가 전부 최대 동시성에 도달하면 → **스케일 업** 신호
- 반쯤 빈 배치로 돌아가는 레플리카가 충분히 많으면 → **스케일 다운** 신호

트래픽 기반 오토스케일링에서 설정할 다섯 가지 (p.188): **min replicas** · **max replicas** · **autoscaling window**(트래픽을 재는 슬라이딩 구간) · **scale down delay**(축소 제안 후 대기 시간) · **concurrency target**.

### 사용률 vs 트래픽 — 둘은 일치하지 않는다

| 판단 근거 | 성격 |
|---|---|
| **Utilization** (GPU 메모리·연산 사용률) | **후행 지표** |
| **Traffic** (처리 중인 요청 수) | **선제적** 판단 가능 |

> LLM prefill에서, 캐시되지 않은 입력 토큰 수십만 개짜리 요청 **몇 개**가 캐시 적중률 높은 작은 요청 **다수**보다 훨씬 높은 사용률을 유발할 수 있습니다. (p.187)

둘을 **조합해서** 쓰라는 게 결론입니다. 1주차의 prefill=compute bound 이야기가 여기서 운영 문제로 되돌아옵니다.

## 3. 콜드 스타트 — 스케일 다운을 못 하게 만드는 것

> 레플리카를 빠르게 띄우지 못하면 **자신 있게 줄일 수 없고**, 결국 과다 프로비저닝으로 이어집니다. (p.190)

콜드 스타트를 넷으로 쪼개서 각각 최적화합니다 (p.191): **GPU 확보** → **이미지 로딩** → **모델 가중치 로딩** → **엔진 기동**(컴파일 포함).

- 이미지·가중치 로딩은 결국 **수백 GB를 얼마나 빨리 쓰느냐**의 문제 → 작게 만들거나 대역폭을 키우거나. **양자화는 콜드 스타트도 빠르게 합니다.** (p.191)
- 예전엔 작은 모델의 가중치를 이미지에 구워 넣었지만, 이제 가중치가 이미지를 압도하므로 **따로 로딩**하는 게 낫습니다. (p.192)
- Hugging Face에서 직접 받으면 **그쪽 egress 속도에 묶이고**, S3는 네트워크 지연과 전송 비용이 붙습니다. 같은 데이터센터 안 GPU 근처에 캐시하는 게 최선. (p.192)
- vLLM·SGLang은 기동이 빠릅니다. TensorRT-LLM이나 최적화된 PyTorch는 **컴파일 단계에 수 분**이 걸리므로 **빌드된 엔진을 캐시**해야 합니다. 단, GPU 타입·CUDA 버전·의존성이 **빌드 환경과 정확히 같아야** 로드됩니다. (p.192)

## 4. 라우팅·로드밸런싱·큐

레플리카가 여럿이면 "이 요청을 어디로 보낼까"가 문제가 됩니다. (p.192)

| 컴포넌트 | 답하는 질문 | 수준 |
|---|---|---|
| **Router** | "이 요청은 **어디로 가야 하나**?" | 요청 단위 |
| **Load balancer** | "이 요청은 **어디로 갈 수 있나**?" | 시스템 단위 |

균등 분배가 목표지만 "레플리카 3개에 요청 12개니까 4개씩"이 안 되는 이유 — **요청마다 입력 토큰 수가 다릅니다.** 대부분 100 토큰인데 하나가 10,000 토큰이면 단순 분배는 무너집니다. (p.193)

똑똑한 라우팅의 두 사례 (p.193):
- **KV cache-aware routing** — 프리픽스가 이미 KV cache에 있는 레플리카로 보냄 *(3주차 prefix caching과 직결)*
- **LoRA-aware routing** — 원하는 LoRA 가중치를 이미 메모리에 올린 레플리카로 보냄 *(5주차 multi-LoRA와 직결)*

그리고 **큐**: 감당 못 할 트래픽이 오면 스케일 업 될 때까지 요청을 붙들고 있어야 합니다. 기본은 FIFO, 유료 사용자 우선 같은 우선순위 큐도 가능. **새 레플리카가 올라오면 큐가 즉시 인지해서 동시성 한도까지 배정**해야 합니다 — 안 그러면 요청이 기존 레플리카만 계속 기다립니다. (p.193)

## 5. 스트리밍과 클라이언트 코드 — CH3에서 놓치기 쉬운 절반

> 추론 엔지니어링은 CUDA부터 쿠버네티스까지 다루지만, 지연 최적화에서 **자주 간과되는 결정적 영역이 클라이언트 코드**입니다. (p.206)

- **TLS 핸드셰이크만으로도** P95 종단간 300ms SLA의 **10% 이상**을 추론 시작 전에 써버립니다. → **세션 재사용** (OpenAI SDK는 내부적으로 해줌) (p.207)
- **비동기 추론** — 대량 문서 처리·코퍼스 임베딩처럼 지연에 둔감한 작업은 "fire and forget"으로. 동기 요청 타임아웃은 보통 **수 분**이지만 비동기 작업은 **수 시간** 단위이고, 결과는 webhook으로 돌려받습니다. (p.207)
- **프로토콜** — 텍스트는 HTTP 스트리밍으로 충분하지만, 실시간 음성·영상은 입출력 양방향이 필요합니다. (p.208)

| 프로토콜 | 쓰는 곳 | 특징 |
|---|---|---|
| **WebSockets** | 스키마 강제가 필요 없는 스트리밍 (오디오 등 비정형) | 서버가 지원하는 동시 연결 수에 **상한**이 있고, 차면 슬롯이 나거나 레플리카가 늘 때까지 대기 |
| **gRPC** | 잘 정의된 **서비스 간** 통신 | 스키마 검증 계층이 있어 파싱 부담이 없는 대신 **WebSockets보다 약간 느림** |

## 6. 성능 측정 ★ CH4의 핵심

### 지표 (p.37)

| TTFT (time to first token) | TPS (tokens per second) |
|---|---|
| 스트리밍에서 **첫 토큰이 보이기까지** | 첫 토큰 이후 **초당 받는 토큰 수** |
| **compute-bound prefill** 기반 | **bandwidth-bound decode** 기반 |
| 낮을수록 좋음 | 높을수록 좋음 |

1주차의 prefill/decode 구분이 그대로 **지표 두 개**로 나뉜다는 게 핵심입니다.

**TPS는 모호한 용어**라서 저자가 구체적인 표현을 권합니다 (p.37):
- **Perceived TPS** — 사용자별 관측 TPS (지연 지표)
- **Total TPS** — 서비스 전체가 초당 생성하는 토큰 수 (처리량 지표)
- **ITL** (inter-token latency) — 토큰 사이 시간. **ITL 10ms = 사용자당 100 TPS**

> 챗봇처럼 출력을 스트리밍하는 시스템엔 TTFT/TPS를 쓰지만, **에이전트의 툴 콜**처럼 토큰이 개별적으로 쓸모없는 요청은 **총 응답 시간**으로 측정합니다. (p.38)

### 평균이 아니라 백분위 (p.39)

> LLM 총 응답 시간은 **right-skewed 분포**입니다. 대부분은 최빈값 근처지만 이상치가 훨씬 오래 걸립니다. **열 번 중 한 번이 몇 초씩 걸리면**, 나머지가 빠릿한 것으론 부족합니다.

P50(2번 중 1번이 더 느림) · P90(10번 중 1번) · P95(20번 중 1번) · P99(100번 중 1번). 평균을 낮추는 것도 중요하지만 좋은 성능 작업은 **P90/P99를 줄이는 데** 집중합니다.

### 추론 시간 vs 종단간 (p.39)

둘 다 알아야 합니다. **추론 시간**은 모델 성능 작업이 잘 됐는지를, **종단간**은 사용자가 체감하는 속도를 알려줍니다.

> **추론 시간은 빠른데 종단간이 느리다면**, 모델 성능 최적화가 아니라 **인프라**를 봐야 합니다.

### 벤치마크를 어떻게 만드나 (p.114)

> 최고의 벤치마크는 **실제 프로덕션 트래픽을 섀도잉**하는 것입니다. 들어오는 요청을 테스트 시스템에 복사해, 원래 요청에 영향을 주지 않으면서 성능을 재는 방식입니다.

섀도잉이 불가능하면 시뮬레이션해야 하는데, **네 가지 차원**을 실제 워크로드에 맞춰야 합니다 (p.115):

| 차원 | 왜 |
|---|---|
| **시퀀스 길이** (ISL/OSL) | TTFT와 메모리 사용량이 입력·출력 토큰 수에 달림 |
| **트래픽 양과 패턴** | 배칭과 서버 부하는 동시 요청 수에 달림. **지터를 넣어** 실제처럼 |
| **요청 내용** | 실제 프롬프트가 **캐시 적중률**과 **draft 토큰 수용률**에 영향 |
| **입력 파라미터** | temperature, reasoning effort 등을 **예상 프로덕션 값**으로 |

> 최적화는 트레이드오프와 제약의 문제입니다. **엉터리 입력에 대고 벤치마크 성능을 극대화하면**, 프로덕션 성능은 기대와 달라집니다. (p.115)

### 벤치마킹 팁 (p.116) — 실습에 바로 쓸 것

- 이상치에 휘둘리지 않을 만큼 **충분한 트래픽**을 보낼 것. 애매하면 **여러 번 돌려 평균**.
- **최적화 작업 전에 탄탄한 기준선(baseline)부터.**
- 최적화를 **개별로도, 조합으로도** 시험할 것 — 무엇이 개선을 이끄는지 알기 위해.
- **최적화끼리 상충할 수 있습니다.** 예: *speculative decoding을 큰 배치 크기와 함께 쓰기* (4주차 복선)
- **한 번에 하나씩만 바꿀 것.** 벤치마크 설정도 실험이니까.

> 이미 [`labs/wsl2-vllm-baseline/`](../labs/wsl2-vllm-baseline/README.md)에 기준선 측정이 있습니다. 여기에 **배치 크기 축만 추가**하면 §1의 트레이드오프를 직접 관측할 수 있고, 그게 2주차 과제 소재가 됩니다.

### 도구 (p.115, p.117)

| 목적 | 도구 |
|---|---|
| 벤치마킹 | **SGLang genai-bench**, **NVIDIA GenAI-Perf**, **Locust**(범용 부하 테스트) |
| 현실적 입력 + 품질 회귀 확인 | 오픈 evals 데이터셋 (MMLU, gsm8k, SWE-bench, HumanEval 등) |
| 프로파일링 | **PyTorch Profiler**, **Nsight Systems(NSys)**, **Nsight Compute(NCU)** |

> **벤치마킹은 시스템이 *어떻게* 동작하는지**, **프로파일링은 *왜* 그렇게 동작하는지**를 알려줍니다. 벤치마크가 "P90 TTFT 350ms"라는 숫자 하나를 준다면, 프로파일러는 그 밀리초가 **어디서 쓰였는지**를 보여줍니다. (p.116)

다만 저자는 **대부분의 추론 엔지니어에게 프로파일링은 일상 업무가 아니라고** 못 박습니다. TensorRT-LLM 같은 고성능 도구를 쓴다면 작업 흐름은 *설정 → 벤치마크*의 반복이고 프로파일링은 불필요합니다. vLLM·SGLang에 기여하거나, PyTorch로 서비스를 직접 짜거나, 영상 생성 같은 최전선에 있을 때 필요합니다. (p.117)

## 7. 서빙 스택 선택 — 오픈소스 3종 (p.107)

교재 CH4의 "오픈소스 vs 클라우드"에 대응하는 부분입니다. 4주차 CH8에서 다시 깊게 다루므로 **지금은 표만 눈에 익혀두면** 충분합니다.

| | **vLLM** | **SGLang** | **TensorRT-LLM** |
|---|---|---|---|
| 성능 | Good | Good | **Best** |
| 사용 난이도 | Easy | Easy | **Hard** |
| 모델 지원 | Most | Most | Some |
| 하드웨어 | GPU, TPU | NVIDIA, AMD | **NVIDIA만** |
| 라이선스 | Apache 2.0 | Apache 2.0 | Apache 2.0 |

셋 다 **continuous batching은 기본 탑재**이고, 주요 최적화(PTQ 양자화·speculative decoding·prefix caching·병렬화·disaggregation)를 지원합니다. (p.108)

- **vLLM** — 시장 점유율 1위(GitHub 스타가 나머지 둘의 합보다 2배). 하드웨어·모델 지원이 가장 넓고 거의 모든 오픈 LLM이 day zero 지원. `vllm serve` + 플래그. (p.109)
- **SGLang** — 빠른 백엔드 런타임 + 유연한 프론트엔드 언어. DeepSeek·Qwen·Kimi 등 중국계 오픈 모델과 함께 부상했고 **xAI의 선택**. **대규모 MoE 다중 노드 배포**에 집중 투자. `sglang.launch_server`. (p.110)
- **TensorRT-LLM** — NVIDIA 엔지니어가 쓴 **클로즈드 커널 포함**이라 최고 성능. ⚠️ **버전 함정**: `0.X.Y`는 TensorRT 플러그인, `1.X.Y`는 TensorRT 의존성이 없는 **독립 PyTorch 기반 패키지**입니다. 어느 쪽을 쓰는지 반드시 확인. (p.111)

## 8. 오케스트레이션 — 교재의 Triton 자리

교재 CH3은 **NVIDIA Triton**을 다루지만, 이 PDF가 그 자리에서 설명하는 것은 **NVIDIA Dynamo**입니다 (2025년 3월 GTC 발표). 세 엔진(vLLM·SGLang·TensorRT-LLM)을 **백엔드로 두고 그 위에 오케스트레이션 계층**을 얹는 구조입니다. (p.113)

Dynamo가 제공하는 것:
- **KV cache 재사용** — 요청 간 KV 유지 + **프리픽스 매치 기반 라우팅**
- **Disaggregation** — prefill과 decode를 **따로 최적화된 엔진으로 분리**, 독립 스케일링 *(4주차 CH7·7주차 llm-d의 핵심)*
- **다중 노드 병렬화** — 보통 Expert Parallelism

> 사용자가 정의한 **TTFT·TPS 제약**을 기준으로 SLA 기반 플래너가 prefill 워커와 decode 워커를 **자동으로 늘리고 줄일** 수 있습니다. (p.113)

**다만 대부분의 배포엔 Dynamo가 과합니다.** disaggregation과 KV 인지 라우팅이 의미 있을 만큼의 물량이 아니라면 불필요한 복잡도이고, 그냥 추론 엔진을 직접 쓰면 됩니다. (p.114)

> 이 챕터의 일반 원칙: **규모가 클수록 쓸 수 있는 최적화 도구와 기법이 많아집니다.** (p.114)

관련해서 **NIM**(NVIDIA Inference Microservices)도 나옵니다 — 인기 오픈 모델용 사전 빌드 Docker 컨테이너. 출발점·레퍼런스 아키텍처·즉시 사용 중 아무거나로 쓸 수 있지만, **최대한의 제어를 원하면** NIM을 개조하기보다 덜 고집스러운 베이스 이미지에서 직접 만드는 게 낫습니다. (p.185)

## 9. 애플리케이션이 설계를 결정한다 (CH4 도입부)

> 모든 추론 엔지니어링 결정은 **유스케이스의 하류에 있습니다.** (p.29)

### 온라인 vs 오프라인 (p.31)

> 추론 엔지니어링의 주요 트레이드오프 하나가 **지연 대 처리량**입니다. 지연이 낮으면 앱이 빨라지고, 처리량이 높으면 **같은 사용자 수를 더 적은 GPU로** 감당해 규모에서 저렴해집니다.

- **온라인** (코드 완성, 챗, 음성 에이전트) → **지연 최적화**
- **오프라인** (카탈로그 전사, 문서 처리, 코퍼스 준비) → **처리량 최적화**

같은 모델이라도 양쪽에 쓰인다면 (예: Whisper를 실시간 받아쓰기 + 배치 전사) **물량이 충분하다면 배포를 둘로 나누는 게 비용 효율적**입니다 — 하나는 지연, 하나는 처리량에 맞춰서. (p.32)

### 앱 카테고리별 고려사항 (p.30-31) — CH4의 에이전틱·RAG가 여기 있음

| 카테고리 | 고려사항 |
|---|---|
| **Agents** | 사용자 동작 **하나가 다수의 추론 호출**을 유발 |
| **Chat** (RAG 포함) | **TTFT**가 챗을 빠르게 느끼게 함 |
| **Voice** | 자연스러운 대화를 위한 **종단간 지연** |
| **Search** | 오프라인 코퍼스 구축 vs 온라인 사용자 요청 |
| **Completion** | **사용자 타이핑 속도**에 맞춘 완성 청크 |

### 다단계 파이프라인 — 에이전틱/RAG의 인프라 문제 (p.194)

AI 앱은 점점 **다중 모델·다단계 복합 워크로드**가 되고, 단계마다 하드웨어 요구가 다릅니다. 음성 활동 감지 모델은 전사 모델보다 훨씬 약한 GPU면 되고, 그 전사본을 처리하는 LLM은 다중 GPU 노드가 필요할 수 있습니다. → **단계별로 오토스케일링을 분해**해야 병목과 과다 프로비저닝을 동시에 피합니다.

> 다만 **파이프라인의 모든 모델은 같은 클러스터 안에서** 돌아야 합니다. 클러스터 내부 전송이 10ms, 클러스터 간 전송이 50ms라면, 5단계 파이프라인에서 그 40ms 차이는 **1초 SLA의 20%**입니다. (p.195)

에이전틱·RAG 이야기를 들을 때 이 문단을 떠올리세요. 아키텍처 다이어그램에서 화살표 하나가 클러스터 경계를 넘으면 그건 공짜가 아닙니다.
