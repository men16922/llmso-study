# FP8 양자화로 처리량이 늘어난 이유

**처리량이 늘었다면, 답변도 빨라진 걸까요?**

한꺼번에 처리하는 요청이 많아져도 초당 토큰 수는 늘어납니다. 그렇다고 내 답변까지 빨리 나오는 건 아닙니다.

FP8 양자화로 처리량이 늘어난 뒤 측정 화면을 살펴봤습니다. 다른 숫자가 눈에 들어왔습니다. **동시에 처리하는 요청은 여전히 16개였습니다.**

요청 수는 같은데, 초당 나오는 토큰은 더 많아졌습니다. 어디서 시간이 줄어든 걸까요?

## 1. 양자화가 빨라지는 두 경로

**처리량 수치만 봐서는 무엇 때문에 빨라졌는지 알기 어렵습니다.**

<details>
<summary>양자화의 두 경로와 교재 사례</summary>

양자화를 켜면 모델이 차지하는 메모리가 줄어듭니다. 남는 공간에 더 많은 요청을 담을 수 있고 가중치를 읽고 계산하는 경로도 바뀔 수 있습니다.

**KV 예산**은 캐시에 이전 토큰의 계산 결과를 얼마나 보관할 수 있는지를 나타냅니다. **ITL**은 사용자가 토큰을 받는 시간 간격입니다. **GEMM**은 모델의 선형 계층에서 하는 행렬 곱셈을 가리킵니다. BF16과 FP8은 각각 16비트와 8비트 부동소수점 형식입니다.

![FP8 양자화의 두 후보 경로. KV 캐시 공간 증가와 토큰 처리시간 단축을 나누고 예산 축소 실험으로 확인한다](./figures/fig-w5-fp8-paths.svg)

*두 경로는 함께 작동할 수 있습니다. 이번에는 KV 예산 증가가 반드시 필요했는지부터 확인했습니다.*

CH9의 Qwen3-14B AWQ 사례에서는 모델 메모리를 줄여 KV 캐시를 확보한 뒤 처리량이 2.7배 늘었습니다. 같은 스터디 자료의 RTX 4070 계열·Qwen3-4B 참고 실습에는 별도의 Nsight 분석이 있습니다. 모델과 측정 조건이 다른 두 사례를 하나의 결과로 합치지는 않았습니다.

제 GPU·모델·양자화 방식은 교재와 모두 다릅니다. **내 환경에서도 KV 예산이 늘어서 빨라졌는지**를 확인하려고 했습니다. 교재 사례의 재현이나 반박을 목적으로 삼지는 않았습니다.

</details>

## 2. KV 예산을 되돌려도 이득은 남았다

**이 조건에서는 늘어난 KV 예산을 줄여도 처리량 이득이 사라지지 않았습니다.**

<details>
<summary>세 구성의 대조 실험과 결과</summary>

실험에는 **RTX 4080 Laptop 12GB·Qwen2.5-1.5B·vLLM v0.23.0**을 사용했습니다.

세 구성을 비교했습니다. BF16을 기준으로 FP8의 성능을 잰 뒤, FP8은 그대로 두고 KV 예산만 BF16 수준에 가깝게 줄였습니다. 세 구성 모두 짧은 입력에서 최대 512토큰을 생성하는 `decode` 워크로드를 동시성 16으로 실행했습니다.

![BF16 1689.3, FP8 2258.8, KV 예산을 줄인 FP8 2261.0 tok/s. 세 구성의 처리량 평균과 표준편차 비교](./figures/fig-w5-fp8-ablation.svg)

*막대는 구성별 3회 측정 평균, 오차 막대는 ±1σ입니다. KV 예산을 줄인 뒤에도 FP8 두 구성의 처리량은 비슷했습니다.*

| 구성 | KV 수용량 지표 | 처리량 (tok/s) | ITL p50 (ms) |
| --- | --- | --- | --- |
| BF16 기본 | 59.50x | 1,689.3 | 9.7 |
| FP8 기본 | 70.20x | 2,258.8 | 7.3 |
| FP8 · KV 예산 축소 | 60.95x | 2,261.0 | 7.3 |

기동 로그의 `Maximum concurrency`로 KV 수용량을 비교했습니다. 요청 하나의 최대 길이를 4,096토큰으로 잡았을 때의 용량입니다. 지금 실행 중인 요청 수를 나타내지는 않습니다. 예산을 줄인 구성도 기준보다는 **2.4% 큰 수준**이었습니다. 예산을 정확히 같게 맞추지는 못했습니다.

FP8 기본의 처리량 이득은 **+33.7%**, 예산을 줄인 구성은 **+33.8%**였습니다. 두 평균은 약 0.1% 차이로, 반복해서 잴 때의 변동보다 작았습니다. 측정은 3회이고 예산에도 오차가 있어, KV 예산의 기여도가 정확히 0%라고 단정하지는 않았습니다.

BF16만으로도 확인해 봤습니다. KV 예산을 64,048→243,696토큰으로 **3.80배** 늘려도 같은 `decode` 부하에서 처리량은 약 **0.5%**만 변했습니다. 예산이 늘수록 빨라지는 추세는 없었습니다. 짧은 입력과 동시 요청 16개에 필요한 KV 공간은 가장 작은 구성에도 충분했습니다.

<summary>실험 환경과 세 구성의 전체 결과</summary>

| 항목 | 값 |
| --- | --- |
| GPU | NVIDIA GeForce RTX 4080 Laptop, 12,282 MiB |
| 커널 | 6.18.33.1-microsoft-standard-WSL2 |

| 모델 | `Qwen/Qwen2.5-1.5B-Instruct` |

전 구성에서 `max_model_len=4096`, `max_num_seqs=64`를 고정했습니다. 양자화에는 같은 BF16 체크포인트에 `--quantization fp8`을 적용했습니다. W8A8 경로에서는 가중치와 활성화의 정밀도가 함께 바뀝니다. KV 캐시 정밀도를 바꾸는 실험은 아닙니다.

| 워크로드 | 입력 | 출력 | 특징 |
| --- | --- | --- | --- |
| **`decode`** | 짧은 입력 | 512토큰 | 새 내용을 길게 생성하는 디코드 지배 워크로드 |
| **`prefill`** | 같은 문단을 24회 반복한 긴 문맥 | 64토큰 | 입력을 되짚는 프리필 지배 워크로드 |

F1b에서는 구성마다 3회씩 측정했습니다. 표에서 σ는 처리량의 표준편차를 뜻합니다. ITL은 이 표에 원기록대로 초 단위를 남겼고 본문에는 ms로 환산해 적었습니다.

| 구성 | util | Maximum concurrency | 처리량 (tok/s, 3회) | σ | vs BF16 | ITL p50 (s) |
| --- | --- | --- | --- | --- | --- | --- |
| ① BF16 기본 | 0.85 | 59.50x | 1,689.3 | 3.3 | — | 0.0097 |
| ② FP8 기본 | 0.85 | 70.20x | 2,258.8 | 6.5 | +33.7% | 0.0073 |
| ③ **FP8 · KV 예산 축소** | 0.7656 | **60.95x** | **2,261.0** | 12.5 | **+33.8%** | 0.0073 |

기존 원고에는 ‘재현 편차 0.38%’라고 적혀 있습니다. 계산식이 남아 있지 않아 판단 근거로 쓰지 않았습니다. 표의 평균과 표준편차로 계산한 BF16 변동계수는 `3.3 / 1,689.3 × 100 ≈ 0.20%`입니다. 표준편차와 최댓값·최솟값의 차이는 다른 통계량이므로 바꿔 쓸 수 없습니다.

양자화 전후 기동 로그와 성능 요약은 다음과 같습니다.

|  | BF16 | FP8 | 차이 |
| --- | --- | --- | --- |
| Available KV cache memory | 6.51 GiB | 7.68 GiB | +1.17 GiB |
| GPU KV cache size | 243,696 토큰 | 287,536 토큰 | +43,840 |
| Maximum concurrency | 59.50x | 70.20x | **+18.0%** |
| decode c=16 처리량 | 1,689.3 tok/s | 2,258.8 tok/s | **+33.7%** |

KV 예산을 맞출 때는 기동 로그의 실측값을 보고 `gpu_memory_utilization`을 조절했습니다. 기존 기록의 조정 과정입니다.

```plain text
attempt 1: conc=70.20x -> next util=0.7204
attempt 2: conc=55.99x -> next util=0.7656
attempt 3: conc=60.95x -> 성립 (기준 59.50x 대비 오차 2.4%, ±5% 이내)
```
최종 예산도 기준보다 2.4% 컸습니다. 정확히 같은 예산으로 오해하지 않도록 본문의 ‘동결’을 ‘KV 예산 축소’로 바꿨습니다.

```bash
# 기동 로그에서 Maximum concurrency 숫자만 꺼낸다
read_conc() {
  kubectl -n llm-serving-lab logs deploy/vllm-baseline \
    | grep -oE 'Maximum concurrency for [0-9,]+ tokens per request: [0-9.]+x' \
    | tail -1 | grep -oE '[0-9.]+x$' | tr -d 'x'
}
```

## 3. 같은 요청 수에서 토큰 간격이 짧아졌다

**사용자가 받는 토큰의 간격도 짧아졌습니다. ITL p50은 9.7ms에서 7.3ms로 24.7% 줄었습니다.**

<details>
<summary>처리량·요청 수 실측 화면과 커널 시간</summary>

ITL에는 서버 밖의 지연도 포함되므로 이 값만으로 GPU의 어느 연산이 빨라졌다고 판단하지는 않았습니다.

Prometheus에서도 BF16과 FP8에 같은 `decode` 부하를 3분씩 가했습니다. 두 구간 모두 실행 요청 16개, 대기 요청 0개, 선점 0회였습니다. 생성 처리량은 **1,703.6→2,269.3 tok/s(+33.2%)**로 늘었습니다. 실행 요청 수가 같으므로, 더 많은 요청을 한꺼번에 처리해서만 빨라진 것은 아닙니다.

Prometheus 원본 화면에서 위쪽은 생성 처리량, 아래쪽은 실행 중인 요청 수입니다. 아래 그래프의 높이가 같은 두 구간을 보세요. 위 그래프에서는 처리량이 달라졌습니다.
