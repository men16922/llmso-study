# LLM 응답은 늦어지는데, CPU는 여유로웠다

**Trainium·EKS에서 동시 요청과 출력 길이를 바꾸며 확인한 대기 시간과 오토스케일링의 관계**

> **핵심 결과**
>
> - 출력 256토큰에서 동시 요청을 4→8로 늘리자 처리량은 약 0.2% 증가했지만 TTFT p95는 약 14배로 늘었습니다.
> - 같은 조건으로 320건을 이어서 보내자 모두 성공했어도 지연 목표를 만족한 요청은 4건, **1.25%**였습니다.
> - 이 추론 부하에서 CPU 기반 HPA의 목표 복제본은 1개로 유지됐습니다. 별도 CPU 부하로 목표를 3개까지 높여도 가속기 자원이 부족해 가용 복제본은 늘지 않았습니다.

## 1. 성공한 요청 가운데 제때 응답한 요청은 몇 개였나

LLM에 보낸 요청 320건이 모두 정상 응답했습니다. 처리량은 약 453토큰/초였고, CPU 사용량도 높지 않았습니다. 성공률과 CPU만 보면 여유가 있는 서비스처럼 보입니다.

그런데 첫 응답을 2초 안에 받은 요청은 4건뿐이었습니다.

이번 실험에서는 첫 내용이 도착하기까지의 시간인 **TTFT**를 2초 이하, 응답이 끝날 때까지의 시간인 **E2E**를 30초 이하로 정했습니다. 두 조건을 함께 만족한 요청의 비율은 1.25%였습니다. 이는 실험용 지연 목표이며, 답변 품질이나 실제 사용자 만족도를 측정한 수치는 아닙니다.

[이전 글](https://app.notion.com/p/3c44c2420ac48157aaebe78f971e05c9)에서는 엔진 설정의 효과와 서빙 구조의 영향을 분리해 비교했습니다. 이번에는 요청을 더 많이 받았을 때 생기는 대기를 관측하고, 오토스케일링이 그 대기에 반응하는지 확인했습니다.

## 2. 동시 요청을 두 배로 늘려도 처리량은 거의 같았다

AWS Trainium `trn1.2xlarge` 한 대에서 EKS와 vLLM·NxD로 TinyLlama-1.1B를 실행했습니다. vLLM의 동시 실행 슬롯은 `max_num_seqs=4`로 고정했습니다. 클라이언트의 동시 요청 수를 늘려도 서버의 슬롯 수는 바뀌지 않습니다.

입력은 같은 짧은 한국어 문장으로 유지하고, 출력 상한은 64·256토큰으로, 동시 요청은 4·8개로 바꿨습니다. 각 조건은 32건씩 3회 반복했습니다. 총 384건 모두 성공했고, 서버가 반환한 생성 토큰 수로 처리량을 계산했습니다.

| 출력 상한 | 동시 요청 | 생성 토큰/초 | TTFT p95 | 지연 목표 충족률 |
| --- | --- | --- | --- | --- |
| 64토큰 | 4 | 371.08 | 0.172초 | 100% |
| 64토큰 | 8 | 373.35 | 0.862초 | 100% |
| 256토큰 | 4 | 452.58 | 0.173초 | 100% |
| 256토큰 | 8 | 453.41 | 2.433초 | 12.5% |

*각 열은 3회 측정의 평균입니다. TTFT p95도 각 실행의 p95를 평균한 값이며, 요청 전체를 합쳐 계산한 p95는 아닙니다. 지연 목표는 TTFT ≤ 2초와 E2E ≤ 30초입니다.*

64토큰에서는 동시 요청을 늘려도 모든 요청이 목표 안에 들어왔습니다. 하지만 256토큰에서는 같은 변경만으로 충족률이 12.5%까지 낮아졌습니다. 동시 요청 4개와 비교하면 처리량 증가는 약 0.2%에 그쳤고 TTFT p95는 약 14배로 늘었습니다.

추가 요청이 기다리고 있다는 해석과 맞는 결과입니다. 출력이 길어지면 먼저 들어간 요청이 실행 슬롯을 더 오래 사용합니다. 뒤에서 기다리는 요청은 그만큼 첫 응답을 늦게 받습니다. 다만 슬롯 수를 바꾸는 대조 실험이나 커널 분석은 하지 않았으므로, 대기의 원인을 전부 이 설정 하나로 설명하지는 않습니다.

## 3. 짧은 시험에서는 첫 네 건의 영향이 컸다

출력 256토큰·동시 요청 8개 조건을 320건으로 늘려 약 181초 동안 실행했습니다. 결과는 **320/320 성공, 452.81토큰/초, TTFT p95 2.447초**였습니다. 지연 목표를 만족한 요청은 처음 네 건뿐이었습니다.

32건 시험에서는 4/32로 12.5%였던 값이, 320건 시험에서는 4/320으로 1.25%가 됐습니다. 처리량과 TTFT p95는 비슷했지만 충족률은 크게 달랐습니다. 시작할 때 슬롯이 비어 있었고, 그때 들어간 요청의 비중이 달라졌기 때문입니다.

짧은 시험만으로 서비스가 지속해서 감당할 동시 요청 수를 판단하기 어려운 이유입니다. 특히 이번처럼 동시 요청 수를 일정하게 유지하는 부하에서는 시작 구간과 요청이 계속 대기하는 구간을 나눠 봅니다.

그동안 오토스케일링은 어떻게 반응했을까요?

## 4. 요청 네 건이 기다려도 CPU HPA는 반응하지 않았다

지속 부하 구간의 Prometheus 시계열을 확인했습니다. 10초 간격으로 조회한 16개 표본 모두에서 **실행 요청 4건, 대기 요청 4건**이 관측됐습니다. HPA의 목표 복제본과 실제 가용 복제본은 모두 1개였습니다.

![실제 추론 부하 중 실행·대기 요청, CPU, 복제본 수를 함께 관측한 Grafana 화면](./screenshots/week6-inference-load-hpa.png)

*2026-09-12 19:36~19:39 KST가 지속 부하 구간입니다. 실행·대기는 각각 4건이지만 복제본은 1개로 유지됩니다. 화면의 TTFT는 서버 histogram 추정치이며, 본문의 클라이언트 측정값과 계산 방식이 다릅니다.*

HPA의 확장 기준은 CPU request 대비 사용률 70%로 정했습니다. vLLM Pod의 request는 4코어였고, 추론 구간 CPU 사용량의 1분 평균 rate 최댓값은 약 0.465코어였습니다. request 대비 약 11.6%로, 설정한 기준에 미치지 않았습니다. CPU 기반 HPA는 이 사용률을 기준으로 복제본 수를 계산합니다. [Kubernetes HPA 문서](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)

**이 부하에서는 CPU 사용률만으로 첫 응답 지연을 감지할 수 없었습니다.** CPU 임계값을 낮추면 이번 조건에서 더 일찍 확장할 여지는 있습니다. 그러나 입력·출력 길이가 달라져도 그 임계값이 같은 지연 목표를 지켜 줄지는 다시 측정해야 합니다.

CloudWatch에서도 Pod CPU·메모리 수집을 확인했습니다. 다만 CloudWatch의 Pod CPU 비율은 노드 CPU 한도, HPA의 비율은 Pod CPU request를 분모로 씁니다. 백분율을 비교하기 전에 어떤 자원을 기준으로 계산했는지 확인해야 합니다. [CloudWatch 지표 정의](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Container-Insights-metrics-EKS.html)

## 5. HPA가 확장을 요청해도 가용 용량은 늘지 않았다

CPU 지표를 실제로 높이면 HPA가 동작하는지도 별도로 시험했습니다. 이때는 LLM 요청 대신 종료 시간이 정해진 CPU 부하를 사용했습니다.

CPU 사용률이 request 대비 약 197%까지 오르자 HPA 목표는 1→2→3개로 늘었습니다. 부하를 멈추면 다시 1개로 줄었습니다. 하지만 이 과정 내내 실제 가용 복제본은 1개였습니다.

![CPU 부하로 목표 복제본은 3개까지 증가했지만 가용 복제본은 1개였던 Grafana 화면](./screenshots/week6-lab6-hpa-recovery.png)

*왼쪽 아래 가용 복제본은 계속 1개입니다. 목표 복제본만 늘었다가 부하 종료 후 줄어들었습니다. 앞 절의 실제 추론 부하와는 별도 시험입니다.*

새 Pod는 Pending 상태에 머물렀습니다. 이벤트에는 Neuron 가속기·CPU·임시 저장 공간 부족이 함께 기록됐습니다. 단일 노드의 가속기 한 개를 기존 vLLM Pod가 이미 사용하고 있었습니다.

이 실험에서는 두 조건을 따로 확인할 수 있었습니다. 추론 부하에서는 **확장 기준이 대기를 감지하지 못했고**, CPU 부하에서는 **확장 요청을 실행할 자원이 부족했습니다**. 목표 복제본 수만 보고 확장에 성공했다고 판단했다면 후자를 놓쳤을 것입니다.

## 6. 지연을 감지할 지표와 확장할 자원을 함께 검증한다

이번 조건에서는 동시 요청을 4개에서 8개로 늘려 얻은 처리량 이득이 거의 없었습니다. 출력 256토큰에서는 대기가 길어졌고, 지속 부하 320건 중 316건은 설정한 첫 응답 목표를 넘었습니다. 그런데 CPU 기반 HPA는 확장을 요청하지 않았습니다.

운영 판단도 이 결과에서 시작할 수 있습니다.

첫째, **출력 길이별로 지연 목표를 만족하는 동시 요청 범위를 확인합니다.** 이번 고정 입력·256토큰 출력의 3회 반복에서는 동시 요청 4개가 목표를 모두 만족했습니다. 이는 다음 검증의 기준선으로 쓸 수 있지만, 모든 입력에 적용할 운영 한도로 확정한 값은 아닙니다.

둘째, **TTFT와 대기 요청 수를 함께 보고 확장 지표를 정합니다.** 이번에는 CPU만으로 지연을 알아채지 못했습니다. 다음 검증에서는 대기 요청 기반 확장이나 요청 수 제한이 실제로 목표 충족률을 회복하는지 비교할 수 있습니다. 해당 정책의 효과는 아직 측정하지 않았습니다.

셋째, **확장이 가용 복제본과 지연 개선으로 이어지는지 확인합니다.** 목표 복제본 증가 뒤에 Pod가 실행될 자원, 모델이 준비될 시간, 요청을 분산할 경로까지 필요합니다. 이번 실험에서 검증한 것은 HPA의 목표 조정이며, 실제 서빙 용량 증설은 달성하지 못했습니다.

**LLM 서빙의 용량은 요청을 모두 처리했다는 사실만으로 판단하기 어렵습니다. 정한 시간 안에 응답하는 요청이 얼마나 되는지 측정하고, 그 비율이 떨어질 때 확장이 실제로 회복시켜 주는지까지 확인하는 것이 이번 실험의 결론입니다.**
