# B3 — KV cache 손계산 vs 엔진 실측

측정 2026-08-21 · 모델 `Qwen/Qwen2.5-1.5B-Instruct` · RTX 4080 Laptop 12,282 MiB · vLLM 0.7.2 (V0)

## 모델 파라미터 (config.json에서 직접 읽음 — 추측 아님)

| 항목 | 값 |
|---|---|
| `num_hidden_layers` | 28 |
| `num_attention_heads` | **12** |
| `num_key_value_heads` | **2** |
| `hidden_size` | 1536 |
| head_dim (= hidden_size / heads) | 128 |
| `torch_dtype` | bfloat16 (2바이트) |

`num_attention_heads`(12) ≠ `num_key_value_heads`(2) → **GQA**. 12개 쿼리 헤드가 2개 KV 헤드를 6:1로 공유합니다.

## 두 공식

교재 CH5의 공식은 **MHA 전제**입니다.

```
토큰당 KV = 2(K,V) × 층 수 × 어텐션 헤드 수 × head_dim × 정밀도
```

| | 공식 | 토큰당 KV |
|---|---|---|
| 교재 그대로 (MHA 가정) | 2 × 28 × **12** × 128 × 2 | 172,032 B = **168.0 KiB** |
| GQA 반영 | 2 × 28 × **2** × 128 × 2 | 28,672 B = **28.0 KiB** |

**6배 차이.** 교재 공식을 그대로 쓰면 KV 소요를 6배 과대평가합니다.

## 검증 — 어느 공식이 로그와 맞는가

엔진이 기동 로그에 정답을 직접 찍어 줍니다 (`max_model_len=4096`, `max_num_seqs=16`, `util=0.85`):

```
model weights take 2.89GiB; non_torch_memory takes 0.04GiB;
PyTorch activation peak memory takes 0.26GiB;
the rest of the memory reserved for KV Cache is 7.00GiB.
Maximum concurrency for 4096 tokens per request: 64.02x
```

KV 예산 7.00 GiB를 요청 하나가 쓰는 양(`토큰당 KV × 4096`)으로 나눕니다.

| | 요청당 KV (4096토큰) | 예측 동시성 | 로그 실측 |
|---|---|---|---|
| 교재 공식 (MHA) | 168 KiB × 4096 = 672 MiB | **10.7x** | |
| **GQA 반영** | 28 KiB × 4096 = **112 MiB** | **64.0x** | **64.02x** ✅ |

**GQA 공식이 소수점 둘째 자리까지 맞습니다.** 교재 공식대로였다면 "동시 요청 10개가 상한"이라고 결론냈을 자리에서, 실제 상한은 64입니다.

> 교재도 이 어긋남을 예고해 뒀습니다 — *"기본적인 멀티헤드 어텐션(MHA) 형태를 사용하는 Llama-2-7b를 사용하겠습니다"*, *"이후 장에서 MQA, GQA, MLA 등 KV 캐시를 축소하고 압축하는 다른 아이디어들을 소개할 예정"*. **그 "이후 장"이 이번 주 CH6**입니다. CH5의 공식이 CH6에서 보정되는 지점이 바로 여기입니다.

## ★ KV 예산은 정적 공식이 아니라 런타임 프로파일링 결과다

2주차에 *"같은 slots=64인데 `Maximum concurrency`가 59.50x / 28.77x로 갈렸다"* 는 미해결 관측을 남겼습니다. 이번 스윕에서 **그 흔들림의 메커니즘이 잡혔습니다.**

| `max_num_seqs` | 활성화 피크 | KV 예산 | Maximum concurrency |
|---|---|---|---|
| 16 | 0.26 GiB | 7.00 GiB | 64.02x |
| 64 | **0.48 GiB** | **6.79 GiB** | **62.04x** |

가중치(2.89 GiB)도 `util`(0.85)도 그대로인데 KV 예산이 줄었습니다. **슬롯을 늘리면 배치가 커져 활성화 텐서 피크가 커지고, 그만큼 KV에 남는 몫이 깎입니다.**

vLLM은 KV 예산을 `총량 × util − 가중치 − 활성화`로 잡는데 이 활성화 항이 **실제로 프로파일링 한 번 돌려서 재는 값**입니다. 그래서 같은 설정이라도 실행 시점 상태에 따라 달라질 수 있습니다.

- **운영상 함의**: 이 값이 흔들려도 **에러가 나지 않습니다.** 조용히 KV 예산이 줄고, 처리량 천장만 낮아집니다. 롤아웃마다 이 로그 줄을 파일로 남겨야 하는 이유입니다.
- 다만 2주차의 59.50x ↔ 28.77x는 2배 차이라 이 3% 수준의 변동만으로는 설명되지 않습니다. **직전 파드의 VRAM 반환 지연 가설은 여전히 유력하며 미확인으로 남습니다.**

## 손계산 절차 (재현용)

```
KV 예산      ≈ VRAM 총량 × gpu_memory_utilization − 가중치 − 활성화
             = 12,282 MiB × 0.85 − 2.89 GiB − 0.26 GiB
             ≈ 10.20 GiB − 3.15 GiB ≈ 7.05 GiB      (로그 실측 7.00 GiB)

토큰당 KV    = 2 × 28 × 2 × 128 × 2 = 28,672 B = 28 KiB      (GQA)
요청당 KV    = 28 KiB × 4096 = 112 MiB
실질 동시성  = 7.00 GiB ÷ 112 MiB = 64.0                      (로그 실측 64.02x)
```
